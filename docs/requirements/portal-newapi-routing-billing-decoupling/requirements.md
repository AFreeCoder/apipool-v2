## 1. 背景

New API 原生以"分组倍率"表达价格。同一个 New API 分组下，各模型共用该分组倍率；虽然可以调整模型基准倍率，但模型基准倍率会影响所有分组，不能用于实现"同一个门户分组下，不同模型使用不同折扣"。

门户网站需要以面向用户的"分组 + 模型折扣"组织产品。例如，同一个门户 `dev` 分组下，GPT 模型可以是 7 折，Claude 模型可以是 5 折。New API 为了表达相同价格，可以把它们拆到不同的倍率分组中。

因此，门户分组不能再与单个 New API 分组固定绑定。门户需要拥有自己的 API Key、分组、模型折扣、余额和计费语义，并通过透明网关按"门户分组 + 门户模型 ID"动态选择 New API 分组、模型和内部凭证。

本需求同时是上线前审查遗留问题的闭环入口：`docs/test/pre-launch-review/` 中"分组重映射后已有 Key 的远端 token group 不迁移导致价差漂移"（R-P1-7）的架构级解法即本需求；`docs/dev/pre-launch-hardening/token-disaster-incident-report.md` 第 15 节列出的六项产品边界（门户自有账本、模型级定价、Key 解耦、透明计费网关、对账关系、备份边界）中，前五项由本需求定义，备份恢复边界另立 feature（见非目标）。

## 2. 已确认的关键决策

以下决策经 2026-07-13 评审确认，构成需求基线：

1. **用户模型**：门户用户与 New API 用户保持一一对应；门户创建用户时，同步创建或绑定对应的 New API 用户（现状能力，保留）。不采用共享服务账号——New API 后台按用户聚合排查问题的能力值得保留。
2. **Key 模型**：用户只能拿到门户 API Key（本地凭证，明文仅创建时展示一次），不能拿到 New API 运行 Key。门户 API Key 绑定一个门户分组，同一用户同一分组可建多把。
3. **运行 Key 粒度**：New API 运行 Key 按"门户用户 + New API 分组"维护，同一逻辑范围只保留一把有效凭证；多把门户 Key 共享运行 Key。
4. **运行 Key 创建时机**：请求时按需创建（懒创建）。不做注册预建、不做建 Key 时补齐、不做路由发布前批量预置、不区分活跃/不活跃用户。
5. **路由粒度**：以"门户分组 + 门户模型 ID"为最小路由单元，映射到"New API 分组 + New API 模型 ID"；映射可版本化调整。
6. **网关改写范围**：网关完成门户鉴权后，必须**剥离请求中全部客户端凭证载体**（一期至少 `Authorization` 与 `x-api-key`——实测 `/v1/messages` 上 `x-api-key` 会覆盖 `Authorization`，见 16.2；扩展端点时同步评估 query key、`x-goog-api-key` 等），再按目标端点注入 New API 运行凭证。**不改写请求体**。门户模型 ID 与 New API 模型 ID 默认恒等；若未来需要模型重命名，通过 New API 渠道层"模型重定向"实现（待 spike 验证），不在网关改写。
7. **计价主体**：用户账单完全由门户计算——门户账本扣费 = 门户价格版本 × 实际 usage。不照抄 New API 的 quota 扣费额入账。
8. **usage 来源**：优先从转发响应中旁路解析（不改写响应）；解析不到时以响应头捕获的 New API 真实请求 ID 定点查询日志回填；批量日志同步作最后兜底。
9. **余额拦截与负余额（一期，路径二）**：一期只做粗闸门（门户钱包余额 > 0 放行，≤ 0 拒绝），不做预占；结算**无条件入账**，允许余额为负——最后一笔放行请求的费用可超过剩余余额。负余额由粗闸门自然阻断后续请求；负余额用户走人工催缴或核销。透支敞口由两道**可执行硬限**约束（见决策 15）。New API 内部预占与扣费照常运行，作为等额参照（注意：价格方向约束下门户价 ≥ New API 价，价差越大 New API 侧对门户余额的兜底越松，不构成门户侧的硬闸）。二期若需精确拦截，预占语义对齐 New API 的 pre-consume 模式（见 16.3）。
10. **余额策略（两阶段）**：
    - **阶段一（上线～计费验证期）**：门户充值成功后向对应 New API 用户等额加额（现状链路复用）；两侧独立记账、独立扣费，定期对账。
    - **阶段二（对账持续无差异后，需显式决策进入）**：New API 余额与门户脱钩，改为大额内部运行池（定期人工补充）；门户账本成为用户余额唯一事实源。等额同步是阶段一策略，不是永久承诺。
11. **价格硬约束（阶段一）**：任一"门户分组 + 模型"的门户成交价 **≥** 其映射的 New API 分组成交价。否则等额余额下 New API 侧先耗尽，用户门户显示有余额但请求被拒。降价的正确姿势是把模型映射到更低倍率的 New API 分组，使两侧价格重新对齐。
12. **差异处理**：余额或用量不一致时，不自动覆盖或修正任意一侧；初期以差异报表 + 人工核查为主，先定位根因，再以有审计记录的人工调整恢复一致。
13. **门户钱包账本（用户余额唯一事实源）**：新建**追加式钱包账本**——充值、请求扣费、退款、人工调整全部为追加流水，余额为流水之和（派生值，可维护物化余额字段加速，随流水原子更新）；内部金额单位为**整数 micro-USD**（10⁻⁶ 美元，兼容 New API quota 粒度），前端按美元格式展示。流水金额**带符号**，方向约定固定：充值 `+C`、请求扣费 `-C`、请求扣费冲正 `+C`、未消费余额退款 `-C`、充值退款/充值冲正 `-C`、人工调整 `±C`。任意冲正流水的绝对值必须等于原流水且符号相反，通过原流水 ID 建立唯一关联，同一原流水不得被重复冲正（幂等约束）。不复用模板 `credit` 体系（FIFO 过期积分语义与后付费计费冲突）；`apipool_ledger_entry` 保留原职责——作为"向 New API 推送加额"这一远端副作用的幂等执行凭证，不承载用户余额。请求账本结算与钱包扣费流水必须**原子写入**，并以 New API 真实请求 ID 幂等，同一请求不得重复扣费。
14. **模型目录与端点能力一致性**：`/v1/models` 与公开模型目录只展示网关当前实际可调用的模型；路由发布前校验目标模型至少存在一个白名单端点支持其调用形态，且必须通过"目标分组 + 模型 + 端点"的**真实冒烟调用硬门禁**（见 7.2.7——New API 渠道无机器可读的端点能力元数据，冒烟是唯一可靠证明）。Responses-only 模型属一期必卖范围，`/v1/responses` 纳入一期白名单（实测通过，见 16.2）。
15. **透支硬限（一期）**：两道可执行边界替代"仅监控"：
    - **每用户风险占用上限**（初始默认 10，运营可配）：风险占用计数覆盖该用户所有"可能已产生远端消费但结算金额尚未确定"的请求——即处于 `open`、`pending_backfill` 的请求及归属该用户的未决 `orphan_remote` 记录，而不只是网络层进行中的请求。占用达到上限时新请求 fail-closed 返回 429；批量日志同步与人工处理不得绕过该闸门。**槽位只能在请求进入 `settled` 或确认无消费的 `failed_unbilled` 后释放**；进入 `unbilled`（回填穷尽）或其他无法确定金额的异常终态时，保持占用或直接冻结该用户，直到人工处理完成。
    - **原子准入不变量**：任何时刻，成功持有风险槽位的未决消费数量不得超过配置上限。"校验上限 + 取得一个槽位 + 持久化对应请求记录"必须是一个跨进程、跨实例的**原子准入操作**——普通的"先查询计数、后插入记录"存在并发突破窗口，不满足要求（与 New API issue #5690 同型的 TOCTOU 竞态）。只有成功取得持久化槽位的请求才允许向 New API 发起推理调用；准入失败 fail-closed 返回 429。终态迁移（`settled`/`failed_unbilled`）与槽位释放必须原子完成，重复终态处理不得重复释放。风险占用以持久化状态为事实源（服务重启、多实例切换后可从请求账本重建），不得仅依赖单进程内存计数；任何失败路径不得留下"已发推理但无槽位"或"永久占槽但无请求记录"的半成品状态。具体事务/锁/原子计数实现留详细设计（15.12）。
    - **透支自动冻结**：用户负余额绝对值超过冻结阈值（初始默认 $10，运营可配）时自动冻结该用户（fail-closed），冻结解除只能由管理员人工执行（配套解封出口）。
    - 最坏透支敞口 = 风险占用上限 × 白名单模型单请求最坏成本。**逐模型最坏成本记录（由模型上下文与最大输出上限决定）是路由发布的前置条件**：缺少记录、记录过期或模型上下文/最大输出配置变化时，路由不得发布、模型不得继续展示为可调用（校验入 7.2.7）。
16. **计费舍入与计费桶（一期定死，不留设计发挥）**：
    - **计费桶归一化**：各协议原始 usage 必须先归一化为**互不重叠**的计费桶（如非缓存输入、缓存读、缓存写 5m/1h、输出），同一 token 不得因同时出现在总量与明细字段而重复计费——OpenAI 系 `prompt_tokens`/`input_tokens` **包含** `cached_tokens` 子集（须扣除后入非缓存桶），Anthropic 系 `input_tokens` 与 cache 字段互斥（直接映射）；reasoning tokens 计入输出桶（无独立单价时继承输出价）。
    - **唯一舍入点**：各桶金额以高精度计算（不中途舍入），单请求全桶**合计后一次性向上取整（ceil）到 1 micro-USD**。不足 1 micro-USD 的请求计 1 micro-USD（即隐含最小扣费），不丢弃、不跨请求携带余数。
    - **冲正复用**：冲正流水的金额绝对值严格等于原流水、**符号与原流水相反**（请求扣费 `-C` 的冲正为 `+C`），通过原流水 ID 唯一关联；禁止按价格重算产生二次差额；同一原流水不得重复冲正。"未消费余额退款"（`-C`，资金离开钱包）与"请求扣费冲正"（`+C`，撤销一笔扣费）是方向相反的两类动作，流水类型必须区分。
    - 金额层对账容差按"门户 ceil 与 New API 自身舍入的口径差"设定预期。

## 3. 目标

### 3.1 产品目标

- 门户可在同一个门户分组下，为不同模型配置不同折扣。
- 用户使用稳定的门户分组、门户 API Key 和门户模型 ID，不感知 New API 内部分组拆分。
- 调整单个模型对应的 New API 分组时，不要求用户更换门户 API Key，也不改变其他模型的路由。
- 门户拥有第一方请求账本，请求明细展示不再依赖 New API 日志镜像。
- 门户和 New API 都能形成可核对的余额、用量与请求记录。
- 能从 New API 请求记录追溯到门户用户；正常路径（及可唯一恢复的崩溃场景）可进一步通过真实请求 ID 关联到门户 API Key、门户分组和门户模型；无法唯一恢复的孤儿消费保证精确归因到用户、分组、运行 Key、模型与扣费，门户 Key 允许为空并进入人工核查（分级保证，见 7.5.2）。

### 3.2 工程目标

- 建立明确且可版本化的模型级路由关系。
- 将用户可见的门户 API Key 与仅供转发使用的 New API 运行 Key 解耦。
- 运行 Key 数量控制在"用户 × 实际使用的 New API 分组"量级（与现状"每门户 Key 一把远端 Key"同量级）。
- 让远端凭证创建、路由切换、计费结算和对账均具备幂等性、可审计性和失败恢复能力。
- 网关数据面保持最小改写面：只换鉴权头，请求体与响应体只读不写。

## 4. 非目标

- 不修改 New API 的分组、倍率、Key 绑定或计费逻辑。
- 不要求 New API 原生识别门户 API Key、门户分组或门户模型 ID。
- 不把门户网关建设成第二套 New API；渠道选择、上游协议适配、上游重试等仍由 New API 负责。网关对请求/响应体的解析仅限白名单端点的模型字段提取与 usage 提取，不做协议转换。
- 不在本需求阶段确定具体数据库表名、网关部署形态或管理后台页面布局。
- 不通过修改模型基准倍率来实现门户模型折扣。
- 不自动执行余额补偿、历史账单改写或两侧余额强制覆盖。
- 一期不做请求级额度预占与精确拦截（二期增强项）。
- 不做自助退款产品化功能；退款为管理员人工流程（见 7.7）。
- 新架构下账本、路由版本、运行凭证等新增资金相关数据的**备份恢复边界不在本需求内，另立 feature**，实现前必须完成该项定义。

## 5. 核心概念与边界

| 概念             | 定义                                                     | 归属                   |
| ---------------- | -------------------------------------------------------- | ---------------------- |
| 门户分组         | 面向用户的产品与权限分组                                 | 门户                   |
| 门户模型 ID      | 用户请求时使用的稳定模型标识（与 New API 模型 ID 恒等）  | 门户                   |
| 门户模型折扣     | 某门户分组下某模型向用户展示和结算的折扣                 | 门户                   |
| 门户 API Key     | 用户创建并用于访问门户网关的本地凭证，只绑定一个门户分组 | 门户                   |
| New API 分组     | New API 内用于倍率、权限和路由的内部细分分组             | New API                |
| New API 运行 Key | 门户网关代表某个同步用户访问某个 New API 分组的内部凭证  | 门户托管、New API 签发 |
| 路由版本         | 一次请求所使用的模型映射配置快照                         | 门户                   |
| 价格版本         | 一次请求所使用的门户折扣及计价配置快照                   | 门户                   |
| 请求账本         | 门户第一方的请求级记录，含路由/价格上下文、usage 与扣费  | 门户                   |
| 门户钱包账本     | 用户余额唯一事实源：充值/扣费/退款/调整的追加式流水      | 门户                   |
| 待回填           | 请求已终态但 usage/扣费尚未确定，等待日志回填的账本状态  | 门户                   |
| 已结算余额       | 排除待回填请求和未确认充值后的可对账余额                 | 两侧分别记录           |

职责边界：

- 门户负责用户鉴权、门户分组权限、模型折扣展示、余额闸门、门户账本计费、路由选择和对账。
- New API 负责内部倍率计费、协议适配、渠道路由、上游请求和自身日志。
- 两侧通过同步用户、New API 运行 Key、真实请求 ID、用量及额度变动记录形成可核对链路。

## 6. 总体关系模型

### 6.1 用户关系

每个门户用户必须对应一个 New API 用户：

```text
portalUserId <-> newapiUserId
```

New API 日志中的用户 ID 或用户名用于识别"来自哪个门户用户"。不使用所有门户用户共享的 New API 服务账号。

### 6.2 模型路由关系

路由以"门户分组 + 门户模型 ID"为最小配置单元：

```text
(portalGroupId, portalModelId)
    -> (newapiGroup, newapiModelId, routeVersion)
```

不得再假设一个门户分组只对应一个 New API 分组。

门户模型 ID 与 New API 模型 ID **默认恒等**（网关不改写请求体中的 `model` 字段）；`newapiModelId` 字段保留用于表达映射关系，但默认与门户模型 ID 相同。若运营需要"门户模型名与上游真实模型名不同"，通过 New API 渠道层"模型重定向"配置实现（待 spike 验证可用性）。

示例：

| 门户分组 | 门户模型 ID     | 门户折扣 | New API 分组 | New API 模型 ID |
| -------- | --------------- | -------: | ------------ | --------------- |
| `dev`    | `gpt-5.5`       |     7 折 | `price-70`   | `gpt-5.5`       |
| `dev`    | `claude-sonnet` |     5 折 | `price-50`   | `claude-sonnet` |

如果后续把 `dev + gpt-5.5` 从 `price-70` 调整到 `price-60`，只发布一条新路由版本；用户仍使用原门户 API Key 和 `gpt-5.5`，其他模型不受影响。

### 6.3 API Key 关系

门户 API Key 和 New API 运行 Key 不建立永久绑定表。每次请求按以下关系动态解析：

```text
门户 API Key
  -> 门户用户 + 门户分组
  -> 门户分组 + 门户模型 ID
  -> New API 分组 + New API 模型 ID（恒等）
  -> 门户用户对应的 New API 用户 + New API 分组
  -> New API 运行 Key（不存在则请求路径内幂等创建）
```

New API 运行 Key 的逻辑唯一范围为：

```text
(portalUserId, newapiGroup)
```

同一用户、同一 New API 分组只保留一把逻辑有效的运行 Key。密钥轮换期间可以同时存在当前版本与短期备用版本，但不能形成多个无管理关系的有效 Key。

示例：用户 U 在门户 `dev` 分组创建 Key A 和 Key B。两把门户 Key 请求 `gpt-5.5` 时，都路由到 U 在 New API `price-70` 分组下的同一把运行 Key；请求 `claude-sonnet` 时，则共同使用 U 在 `price-50` 分组下的运行 Key。

### 6.4 方案取舍记录

| 方案                                                    | 结论     | 原因                                                                                    |
| ------------------------------------------------------- | -------- | --------------------------------------------------------------------------------------- |
| 所有门户用户共用一个 New API 服务账号                   | 否决     | 失去 New API 后台按用户聚合与排查能力；Key 数量优势在当前体量下不构成决策因素           |
| 每把门户 Key 在每个可能的 New API 分组下都创建远端 Key  | 否决     | Key 数量随"门户 Key × New API 分组"增长，轮换、禁用、删除和审计成本过高                 |
| 一把门户 Key 永久绑定一把 New API Key                   | 否决     | 同一门户分组下的不同模型可能进入不同 New API 分组，且映射会调整（现状架构的根本缺陷）   |
| 路由发布前为受影响用户批量预置运行 Key                  | 否决     | 引入批量远端作业、活跃/不活跃分界与发布门槛；懒创建在无预占的一期形态下更简单且无副作用 |
| 每用户每实际使用的 New API 分组一把运行 Key，请求时创建 | **采用** | 保留用户识别与分组约束；多门户 Key 复用；数量与现状同量级；逻辑最简                     |
| 以 New API 日志的 quota 扣费额直接作为门户入账金额      | 否决     | 门户折扣将无法独立于 New API 倍率；对账退化为同源复读，失去核对意义                     |
| 门户按自有价格版本计价，New API 扣费仅作对账参照        | **采用** | 支撑运营独立调价；对账保留独立信息量（用量层硬核对 + 金额层理论关系核对）               |
| 发现余额差异后自动以一侧覆盖另一侧                      | 否决     | 会破坏证据并掩盖根因，无法形成可信账单                                                  |

## 7. 功能需求

### 7.1 门户 API Key

1. 用户可在同一门户分组下创建多把门户 API Key。
2. 每把门户 API Key 只绑定一个门户分组，并拥有独立名称、状态、创建时间、最后使用时间和撤销记录。
3. 门户 API Key 的明文只在创建时展示；服务端只保存安全校验所需信息（如哈希与前缀掩码）。
4. 创建门户 API Key 是纯本地动作，不触发任何远端调用。
5. 门户 API Key 的启用、禁用和删除由门户网关本地执行。禁用或删除一把门户 API Key，不得禁用该用户共享的 New API 运行 Key，也不得影响该用户的其他门户 API Key。
6. 用户被禁用时，门户必须立即阻止其所有请求，并禁用或撤销该用户全部 New API 运行 Key。

### 7.2 模型级路由配置

1. 每条有效路由必须包含门户分组、门户模型 ID、New API 分组、New API 模型 ID、状态和版本。
2. 同一时刻，一个"门户分组 + 门户模型 ID"只能有一个对新请求生效的路由版本。
3. 修改映射时必须生成新版本，不能让已开始的请求读取到中途变化的映射。
4. 请求开始后必须锁定路由版本、价格版本、New API 分组、New API 模型 ID 和运行凭证版本。
5. 路由版本发布后即时生效；所需运行 Key 由后续请求按需创建，发布不设凭证预置门槛。
6. 停用路由后，门户不得再接受该组合的新请求，但必须保留历史版本用于账单和日志解释。
7. 路由发布前必须通过以下校验，任一失败则拒绝发布：
   - 目标 New API 分组存在、倍率有效；
   - 目标分组属于同步用户可用分组集合（New API `UserUsableGroups` 配置）——否则运行 Key 可创建成功但推理 403（实测机制见 16.2）；维持不变量"所有路由目标分组 ⊆ UserUsableGroups"，该配置由运营维护；
   - 目标模型的调用形态被至少一个白名单端点支持（见 7.5.1），防止"目录可见、调用 404"；
   - **逐渠道可归因冒烟硬门禁**：枚举目标分组内每个可能承接"该模型 + 该端点"的启用渠道，对**每个候选渠道分别**执行可归因到具体渠道的最小真实调用，全部通过方可激活。分组级一次普通选路请求不算数——它只证明当时被选中的那一个渠道（同分组混合支持/不支持某端点的渠道时，选路成功具有偶然性）。可归因验证的实现路径：优先使用 New API 渠道测试接口（`GET /api/channel/test/{channelId}?model=...`，实测存在且可归因，见 16.2；能否覆盖非 Chat 端点待设计确认），不能覆盖的端点用临时隔离/专用测试分组逐渠道冒烟。验证证据至少记录渠道 ID、模型、端点、配置版本与验证时间。渠道新增、启停、换绑分组、模型映射或协议配置变化后，相关验证**立即失效**，重新验证通过前路由不得继续承诺该端点可用。验证失败的组合不得发布、对应模型不得进入可调用目录；
   - **逐模型最坏成本记录存在且未过期**（决策 15）：缺失或失效时不得发布；
   - 价格方向约束（见 7.6.3）。

### 7.3 New API 运行 Key 池

1. 运行 Key 按"门户用户 + New API 分组"维护，不按门户 API Key 维护。
2. 运行 Key 必须绑定该用户对应的 New API 用户和目标 New API 分组。
3. 运行 Key 必须为服务端内部凭证，不得返回浏览器、客户端或用户。
4. 运行 Key 阶段一不设独立额度上限，共享该 New API 用户的账户额度，避免多个分组 Key 各自切分额度。**阶段二注意**：脱钩后 New API 用户额度变为大额内部池，无上限运行 Key 的泄漏爆炸半径变大，届时必须重新评估 Key 级限额或内部池分层。
5. 运行 Key 可限制允许模型集合；启用时至少覆盖当前所有指向该分组且该用户可访问的模型。
6. 创建、查询和轮换运行 Key 必须幂等。并发创建时，最终只能有一个逻辑有效凭证。
7. 运行 Key 停用或删除前，必须确认没有活跃请求仍依赖它，并保留安全宽限期。

### 7.4 New API 运行 Key 的创建时机

1. 门户用户注册时，只同步创建或绑定 New API 用户，不预创建任何运行 Key。
2. 创建门户 API Key 时不创建运行 Key（纯本地动作）。
3. 请求转发时发现"门户用户 + 目标 New API 分组"无有效运行 Key，则在请求路径内**按需幂等创建**：
   - 以本地唯一约束（`portalUserId + newapiGroup`）加占位记录抢占，抢到者调用 New API 创建远端 Key，未抢到者短暂等待复查；
   - 并发场景最终只允许一把逻辑有效凭证存在；
   - 创建成功后该请求继续正常转发，后续请求直接复用。
4. **远端幂等与收编**：New API 创建 token 接口无业务幂等键，同名 token 可重复创建（实测确认）。因此运行 Key 必须使用**稳定且可重建的远端名称**（如 `portal-{portalUserId}-{newapiGroup}` 规范），任何创建/重试前先按稳定名称查询远端（token 搜索接口，实测可用）：已存在则**收编**为本地凭证记录，不存在才创建。该规则覆盖"远端创建成功、本地写回前崩溃"的恢复场景——禁止简单清理占位后盲目重建。
5. 远端创建失败时，该请求返回可重试错误并清理占位记录，不留半成品状态；用户或客户端重试即可恢复（重试路径同样先查询收编）。
6. 每个"用户 × 分组"组合仅首次请求承担一次远端创建延迟（百毫秒级），属可接受代价。

### 7.5 网关数据面

#### 7.5.1 端点白名单（一期）

网关一期仅代理以下端点，其余路径明确返回 404，不做默认透传：

| 端点                   | 协议格式         | 模型字段       | usage 提取位置                                                                                                                                                                                                                                               |
| ---------------------- | ---------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/v1/chat/completions` | OpenAI Chat      | 请求体 `model` | 非流式：响应体 `usage`；流式：末尾含 `usage` 的 chunk（字段 `prompt_tokens`/`completion_tokens`）                                                                                                                                                            |
| `/v1/responses`        | OpenAI Responses | 请求体 `model` | 非流式：响应体 `usage`；流式：`response.completed` 事件内 `response.usage`（默认带）。字段 `input_tokens`/`output_tokens` + `input_tokens_details.cached_tokens`/`cache_write_tokens` + `output_tokens_details.reasoning_tokens`（实测，与 Chat 字段名不同） |
| `/v1/messages`         | Anthropic        | 请求体 `model` | 流式：`message_start` + `message_delta` 事件（默认带）；非流式：响应体 `usage`（字段 `input_tokens`/`output_tokens` + cache 细分）                                                                                                                           |
| `/v1/embeddings`       | OpenAI Embedding | 请求体 `model` | 响应体 `usage`                                                                                                                                                                                                                                               |
| `/v1/models`           | OpenAI 兼容      | —              | 本地实现：返回该门户 Key 所在分组中**网关实际可调用**的门户模型目录（按端点能力过滤），不透传 New API 列表                                                                                                                                                   |

`/v1/responses` 属一期范围（Responses-only 模型为一期必卖商品；OpenAI 官方主推方向）。**运营约束（实测确认）**：New API 对 `/v1/responses` 仅做原生转发、不做协议转换，因此售卖 Responses 形态模型的渠道，其上游必须原生支持 Responses API；渠道配置时必须实测验证（不支持的上游报错如 "messages is required"）。

扩展新端点（image、audio 等）时，必须先定义其模型字段与 usage 提取规则并实测，再纳入白名单。

#### 7.5.2 请求处理流程（一期）

1. 校验门户 API Key，取得门户用户和门户分组。
2. 校验用户、门户 API Key、门户分组和目标模型均处于可用状态（含用户未被透支自动冻结，见决策 15）。
3. 解析请求体 `model` 字段（只读，不改写），使用"门户分组 + 门户模型 ID"解析并锁定路由版本和价格版本。
4. 余额粗闸门：门户钱包余额 > 0 放行，≤ 0 拒绝。不做预占。（可附加风险占用的非原子快速预检以提前拒绝，但不构成准入依据。）
5. 取得该用户在目标 New API 分组下的有效运行 Key；不存在则按 7.4.3 在请求路径内创建（含查询收编）——刻意置于原子准入之前，避免运行 Key 创建失败长期占用风险槽位。
6. **原子准入**（决策 15）：以一个跨进程原子操作完成"校验风险占用上限 + 取得槽位 + 持久化请求账本 `open` 记录（门户请求 ID、用户、门户 Key、门户模型、路由/价格版本、`remoteAttemptAt`）"。准入失败返回 429，且不得发出任何远端推理请求；准入成功即保证网关随后任何时点崩溃，都存在可供恢复归属的先写记录。
7. **剥离请求中全部客户端凭证载体**（一期至少 `Authorization` 与 `x-api-key`），按目标端点注入 New API 运行凭证；请求体原样转发。
8. 转发给 New API；New API 继续负责协议适配、渠道选择和上游调用。
9. 捕获响应头中的 New API 真实请求 ID（`X-Oneapi-Request-Id`，实测含错误响应均返回），回填到 `open` 账本记录。
10. 旁路解析响应（不修改下发内容）提取 usage；流式请求以透传优先，解析失败不得影响用户侧数据流。
11. 请求终态后：
    - 解析到 usage → 按决策 16 归一化计费桶并按锁定的门户价格版本计算扣费（合计后 ceil 到 micro-USD），请求账本结算与钱包扣费流水**原子写入**（按真实请求 ID 幂等）；结算不做余额校验，允许产生负余额（见决策 9）；结算后负余额超过冻结阈值 → 自动冻结用户并告警（决策 15）；进入 `settled`/`failed_unbilled` 时**状态迁移与槽位释放原子完成、重复终态处理不重复释放**，`pending_backfill` 期间保持占用；
    - 未解析到 usage → 账本记录置为"待回填"，延迟数秒以真实请求 ID 定点查询 New API 日志（`GET /api/log/self?request_id=...`，实测支持）回填 usage 与扣费；
    - 定点回填仍失败 → 留待批量日志同步兜底，并纳入待回填积压监控。
12. 流式请求在流结束、客户端中断或超时后必须进入终态处理（同上），不允许账本记录长期停留在非终态。

**崩溃窗口恢复**：若网关在发出远端请求后、捕获响应头前崩溃，账本存在无真实请求 ID 的 `open` 记录。批量日志同步除处理待回填外，还必须**扫描 New API 日志中门户账本不存在的真实请求 ID**（孤儿远端消费）：优先按（运行 Key、模型、时间窗）与无 ID 的 `open` 记录匹配恢复；无法唯一匹配时记为 `orphan_remote` 交人工核查。归属保证等级：**归用户始终精确**（运行 Key 即"用户 + 分组"，计费扣款不受影响）；归具体门户 API Key 在该崩溃窗口内尽力而为——此为已接受的弱化边界，不追求通过修改 New API 实现强保证。

#### 7.5.3 二期增强（本期不实现，设计需预留）

- 请求级额度预占与精确拦截：语义对齐 New API pre-consume 模式（按 `max(promptTokens, 常量) + max_tokens` 估算预扣、高余额信任旁路、终态多退少补、失败异步退还，见 16.3）。
- 请求体注入 `stream_options.include_usage`（实测无副作用）以提高流式 usage 的响应内命中率。
- 二期引入预占后，流程顺序必须为"先取得/创建运行 Key，再预占"，避免预占后执行远端创建副作用。

### 7.6 门户价格与 New API 倍率

1. 门户以"门户分组 + 门户模型 ID"为粒度配置和展示折扣。
2. New API 使用目标分组倍率和模型倍率执行内部计费；门户不干预，也不以其结果入账。
3. **价格方向硬约束（阶段一）**：任一有效路由的门户理论成交价必须 ≥ 目标 New API 分组理论成交价（允许在已批准的舍入容差内相等）。发布路由或价格配置前必须校验该约束，违反则拒绝发布。原因：等额余额下门户价更低会使 New API 侧余额先耗尽，用户"有余额却被拒"。
4. 运营降价通过"调整门户折扣 + 将模型映射到更低倍率的 New API 分组"成对完成，使两侧价格重新对齐；不允许通过两侧价格长期脱钩实现。
5. 价格变更必须版本化；请求结算使用请求开始时锁定的价格版本。
6. **价格版本必须覆盖全部实际计费维度**：除输入/输出单价外，至少包含 cache read、cache write（含 Anthropic 5m/1h 细分）等计费桶的单价或倍率（实测响应 usage 中这些维度真实出现且占比可观）；reasoning tokens 无独立单价时继承输出价。仅存输入/输出价无法正确结算。计费桶归一化、唯一舍入点（合计后 ceil 到 micro-USD）与冲正复用规则按决策 16 执行。
7. 不能通过全局修改模型基准倍率来解决单个门户分组的模型折扣问题。
8. New API 分组、倍率与渠道挂载由运营人员维护；两侧价格一致性由发布时校验保证，运行期漂移由对账暴露（初期不建独立监控）。

### 7.7 充值、余额与退款

**门户钱包账本**（用户余额唯一事实源，见第 2 节决策 13）：追加式流水账本，流水类型至少包含充值（`+`）、请求扣费（`-`）、扣费冲正（`+`）、余额退款（`-`）、充值退款（`-`）、人工调整（`±`）。唯一余额闭合公式为**带符号流水求和**：

```text
期末余额 = 期初余额 + Σ 本期流水 signedAmount
```

（若按业务类型展开为"期初 + 充值 − 扣费 − 退款 ± 调整"形式，其中"扣费""退款"指非负绝对值，不是账本字段中的带符号金额——两种表达不得混用。）内部单位整数 micro-USD，前端按美元展示。流水一经写入不可修改，冲正以符号相反的关联流水表达。

1. **阶段一**：门户充值成功后，钱包账本记正向流水，同时向同一用户的 New API 账户增加等额额度（复用现状兑换码链路及其幂等、失败分级与对账升级机制；`apipool_ledger_entry` 继续作为该远端推送的幂等执行凭证）。
2. 充值同步必须幂等，同一业务充值不得在 New API 重复增加额度。
3. 门户是用户访问拦截和用户账单的执行入口；New API 余额在阶段一作为等额参照与次级防线——但注意两点局限：价格方向约束（门户价 ≥ New API 价）下，价差越大 New API 侧余额消耗越慢、对门户余额的拦截越松；且其自身存在高并发竞态透支窗口（见 16.3）。**不得将 New API 余额描述或依赖为门户余额的等价硬闸**；门户侧的余额控制以粗闸门 + 负余额语义（见第 2 节决策 9）自洽闭环。
4. **阶段二（进入条件：对账连续多个周期无不可解释差异 + 显式决策）**：停止等额同步，New API 用户额度改为大额内部运行池并定期人工补充；门户账本成为用户余额唯一事实源；7.6.3 价格方向约束随之解除；对账退化为用量单向核验 + 内部池水位监控。账本与对账实现必须预留该模式切换开关，避免届时重构。
5. 对账比较必须以已结算状态为准，明确排除或单列：进行中充值、待回填请求、未结束的流式请求、异步日志延迟和舍入差异。
6. 不允许通过给 New API 用户设置与实际充值无关的大额初始额度来掩盖差异（阶段一）。
7. **退款**：不做自助退款。政策为"未消费余额可退，已消费不退，限时间窗口"（具体窗口由运营定）。管理员人工流程，顺序固定：
   1. 管理后台冻结用户；
   2. 门户钱包账本写入退款负向流水，并等额扣减 New API 用户额度（管理员接口直接调整 quota；注意兑换码链路只能加不能减）；
   3. 两侧扣减确认成功后，再到 Stripe 控制台对原支付发起退款；
   4. 全程留审计记录（原因、操作人、关联订单、调整前后余额）。
      被动争议（chargeback）到达时：立即冻结用户 + 负向记账 + 转人工处理。

### 7.8 请求识别与审计账本

New API 日志可按 New API 用户 ID 或用户名识别对应的门户用户，并记录运行 Key、New API 分组、模型、输入/输出用量、扣费和真实请求 ID（日志接口返回 `request_id` 与 `upstream_request_id` 字段，实测确认）。

门户请求账本为每次请求保存以下关联信息：

- 门户请求 ID；
- New API 真实请求 ID（从响应头 `X-Oneapi-Request-Id` 捕获，实测全场景返回，含错误响应）；
- 门户用户 ID；
- 门户 API Key ID，不保存明文；
- 门户分组 ID；
- 用户请求的门户模型 ID；
- 实际 New API 分组和模型 ID；
- 路由版本与价格版本；
- 使用的 New API 运行凭证 ID 或版本，不保存明文；
- 请求开始、结束及终态时间；
- 输入、输出及其他计费单位（usage 来源标记：响应解析 / 日志回填）；
- 门户扣费（按门户价格版本）；
- 回填与对账状态。

**禁止使用 New API 日志接口返回的 `id` 字段作任何标识**——实测该字段是按时间倒序的动态排名（最新恒为 1，随新日志漂移），不是稳定行 ID；现有 `usage_log_snapshot.newapiRequestId` 存的即此值，属坏数据，新账本必须以真实请求 ID 为唯一关联键。

**请求明细展示**：Dashboard 请求记录改读门户请求账本（第一方数据，实时落库），费用字段允许短暂"计费中"状态（回填延迟秒级）。不再以 New API 日志镜像作为展示数据源；现有 `usage_log_snapshot` 明细快照随切换废弃。

追溯语义（分级保证，与 7.5.2 崩溃窗口恢复一致）：

- 在 New API 后台，可直接识别请求属于哪个同步用户、哪个 New API 分组和哪把运行 Key。
- **正常路径及可唯一恢复的请求**：通过真实请求 ID 回查门户请求账本，精确到门户 API Key、门户分组、门户模型、路由/价格版本。
- **`orphan_remote` 记录**：保证精确归因到门户用户、New API 分组、运行 Key、模型、usage 与扣费；门户 API Key 与路由/价格版本允许为空，进入人工核查。

### 7.9 对账与人工纠偏

对账分两层口径：

1. **用量层（硬核对）**：同一请求两侧的 prompt/completion tokens 必须一致——token 数是物理事实，不一致即异常。
2. **金额层（理论关系核对）**：门户扣费与 New API quota 扣费按两侧价格配置的理论关系核对；配置一致时应在已批准舍入容差内相等。**舍入差异是双侧独立计算的常态而非异常**，容差阈值按此设计，防止告警噪音淹没真差异。价差可解释的差异（如调价窗口）与不可解释的差异（bug）必须区分标注。

对账层级：请求级（按真实请求 ID 一对一）、用户周期汇总级、余额级（期末 = 期初 + Σ 带符号流水，与 7.7 唯一闭合公式同口径）。

初期从简：差异报表 + 告警 + 人工核查，不建工单状态机。发现差异后：

1. 记录差异快照和证据，不覆盖原始数据。
2. 优先定位并修复根因（路由版本错误、用量解析错误、重复充值、漏记账、舍入规则不一致、日志延迟等）。
3. 根因修复后，由管理员创建带原因、操作人、关联请求/账单和调整前后余额的补偿记录，人工恢复两侧一致。
4. 不自动修改余额，不回写或删除历史账单，不用"以某一侧为准"静默覆盖另一侧。

如差异持续扩大、无法解释或可能导致超额访问，可临时阻断受影响用户或模型路由；该阻断是风险控制，不是自动余额修正。

### 7.10 配置变更与回滚

1. 路由、价格和运行凭证变更必须留存操作人、时间、变更前后内容和版本。
2. 路由/价格发布前必须通过合法性校验（含 7.6.3 价格方向校验）；发布后即时生效，无凭证预置门槛。
3. 发布失败时，旧版本继续生效。
4. 回滚通过重新激活已知可用的历史版本或发布修正版完成，不直接篡改历史记录。

## 8. 状态要求

### 8.1 门户 API Key 状态

```text
active -> disabled -> deleted
   ^          |
   +----------+
```

- `active`：可接受请求（创建即 active，无 provisioning 态——创建是纯本地动作）。
- `disabled`：本地禁止使用，但保留历史记录，可按权限恢复。
- `deleted`：不可恢复使用，历史请求仍可追溯。

### 8.2 New API 运行凭证状态

```text
pending -> active -> rotating -> retired
   |          |
   +-> failed +-> invalid
```

`pending` 为请求路径内创建的占位态，创建失败转 `failed` 并清理，不阻塞后续重试。

### 8.3 路由状态

```text
draft -> active -> retired
```

只有 `active` 路由可以接收新请求。发布即激活，无 provisioning/failed 中间态（无预置依赖）。

### 8.4 请求账本终态

```text
open -> settled                     （响应解析到 usage，即时结算；余额可为负）
open -> pending_backfill -> settled （日志回填成功）
open -> pending_backfill -> unbilled（回填穷尽仍失败，进人工核查）
open -> failed_unbilled             （请求失败且无消费）
（无门户记录的远端日志）-> orphan_remote（崩溃窗口孤儿消费：批量同步发现、无法唯一匹配 open 记录，进人工核查）
```

不允许账本记录无限期停留在 `open` 或 `pending_backfill`；`settled` 允许产生负余额（负余额由粗闸门阻断后续请求，人工催缴/核销）。

风险占用语义（决策 15）：`open`、`pending_backfill` 与未决 `orphan_remote` 计入该用户风险占用；`settled` 与 `failed_unbilled` 释放占用；`unbilled` 保持占用或触发用户冻结，直至人工处理完成。进入 `open` 必须经由原子准入（校验上限 + 取槽 + 持久化一体），终态迁移与槽位释放原子且幂等——任何时刻持有槽位的未决消费数不得超过上限。

## 9. 逻辑数据约束

1. 一个门户用户只能绑定一个有效 New API 用户，一个 New API 用户不能同时绑定多个门户用户。
2. 一个"门户分组 + 门户模型 ID"同一时刻只能有一个生效路由版本。
3. 一个"门户用户 + New API 分组"同一时刻只能有一个当前有效运行凭证版本（数据库唯一约束 + 占位抢占实现并发收敛）。
4. 门户 API Key 标识全局唯一；密钥摘要或前缀不能泄露完整凭证。
5. 门户请求 ID 全局唯一。
6. 请求账本以 New API 真实请求 ID 作唯一关联键并具备幂等约束，重复同步/回填不得重复入账；禁止使用日志接口的动态排名 `id`。
7. 充值业务单号、退款单号和余额人工调整单号必须具备幂等约束。
8. 路由历史、价格历史、请求账本和余额调整历史不可被普通配置更新覆盖。

## 10. 异常处理

| 场景                         | 预期行为                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------- |
| 门户 Key 无效或已禁用        | 网关直接拒绝，不请求 New API                                                                |
| 门户钱包余额 ≤ 0             | 网关直接拒绝，不请求 New API                                                                |
| 找不到模型路由               | 返回明确的模型不可用错误，不使用默认 New API 分组兜底                                       |
| 非白名单端点                 | 返回 404，不透传                                                                            |
| 运行 Key 缺失                | 请求路径内先按稳定名称查询收编、无则幂等创建；失败返回可重试错误并清理占位，不留半成品      |
| 运行 Key 失效或分组不一致    | 拒绝该请求并标记凭证异常，进入修复流程                                                      |
| New API 请求失败且未消费     | 账本记 `failed_unbilled`，不扣费                                                            |
| New API 已消费但门户响应未知 | 账本置待回填，以真实请求 ID 定点查日志确定终态；不重复发送请求                              |
| 响应未解析到 usage           | 账本置待回填 → 定点日志回填 → 批量同步兜底 → 穷尽后进人工核查                               |
| 结算金额大于剩余余额         | 照常原子入账，余额转负；后续请求被粗闸门拒绝；负余额进入人工催缴/核销                       |
| 用户风险占用达到上限         | 新请求 fail-closed 返回 429，直至有请求进入 `settled`/`failed_unbilled` 释放槽位            |
| 回填穷尽（`unbilled`）       | 保持风险占用或直接冻结用户（fail-closed），进入人工核查，处理完成后才释放                   |
| 网关发出请求后崩溃           | 先写 `open` 记录保证归属可恢复；批量同步扫描孤儿 request ID，无法唯一匹配记 `orphan_remote` |
| 流式请求中断                 | 进入终态处理，按可得 usage（响应或日志）结算，标记中断原因                                  |
| New API 日志暂未可见         | 保持待回填并计入积压监控，不立即判定余额错误                                                |
| 两侧用量或金额不一致         | 告警、保留证据、人工核查根因，不自动修正                                                    |

所有对外错误都必须包含门户请求 ID；内部日志还应包含路由版本和凭证 ID，便于定位。

## 11. 安全要求

1. New API 运行 Key 必须加密存储，仅在服务端转发时解密使用。
2. New API 运行 Key 不得出现在门户响应、浏览器日志、前端状态、公开 API 或普通管理员导出中。
3. 门户网关与 New API 之间必须使用安全网络和传输通道。
4. New API `/v1` 数据面应只允许门户网关或受信内部网络访问，防止用户绕过门户计费与余额拦截直接调用。
5. 日志和错误信息不得打印完整门户 API Key 或 New API 运行 Key。
6. 所有配置发布、人工余额调整、退款、运行凭证轮换和用户禁用操作必须进入审计日志。

## 12. 管理与可观测性需求

管理端至少需要支持：

- 查看门户分组下各模型的折扣、New API 分组/模型映射及当前路由版本；
- 发布映射/价格前查看全部发布校验结果（价格方向、目标分组 ⊆ UserUsableGroups、端点能力覆盖）；
- 按门户用户查看对应 New API 用户、各分组运行 Key 状态和最后使用时间；
- 按门户请求 ID 或 New API 真实请求 ID 查询完整转发链路；
- 查看对账差异报表（用量层/金额层分列，可解释/不可解释分类）；
- 查看人工补偿与退款记录；
- 查看因路由失败、余额不足、凭证异常或回填穷尽而异常的请求。

关键指标至少包括：

- 网关请求成功率和延迟；
- 路由解析失败数；
- 运行 Key 请求路径内创建的次数、耗时与失败数；
- usage 响应内解析命中率（衡量回填依赖度）；
- 待回填积压数量及最长等待时间；
- 门户与 New API 请求关联成功率；
- `orphan_remote` 记录数量；
- 负余额用户数与透支总敞口金额；
- 风险占用闸门 429 次数、各用户当前风险占用水位与透支自动冻结触发次数；
- 路由逐渠道验证失败次数与失效待重验的路由组合数；
- 用户余额差异数量、金额和持续时间；
- 路由或价格版本发布失败数。

## 13. 实施分期与迁移

### 13.1 实施分期

| 期   | 范围                                                                                                       | 验收基准         |
| ---- | ---------------------------------------------------------------------------------------------------------- | ---------------- |
| ①    | 数据结构与管理面基础：模型级路由表、运行 Key 池、钱包账本结构（不影响线上真实调用）                        | 14.1、14.2、14.3 |
| ②    | 网关数据面上线：白名单端点转发、凭证剥离与注入、请求账本、usage 解析与日志回填、余额粗闸门、Dashboard 切换 | 14.4、14.5、14.6 |
| ③    | 对账报表（用量层 + 金额层）与人工纠偏流程、退款 runbook                                                    | 14.4 对账项      |
| 二期 | 预占与精确拦截、include_usage 注入、阶段二余额脱钩                                                         | 另行立项         |

**上线门禁**：① 与 ② 构成同一个不可拆分的上线门禁——① 的路由/Key 池在网关切流前不参与真实调用，**R-P1-7（分组重映射漂移）只有在 ② 完成切流、旧 Key 作废、模型级路由实际生效后才能关闭**。③ 须在 ② 上线后的第一个对账周期内就位。

### 13.2 旧语义替换

1. **"一个门户分组固定映射一个 New API 分组"**替换为"门户分组 + 门户模型 ID 映射 New API 分组 + New API 模型 ID"。
2. **"一把门户 API Key 就是一把 New API Key"**替换为"门户 API Key 为本地用户凭证，New API 运行 Key 为服务端共享运行凭证"。
3. **"门户 Key 的禁用/删除同步禁用/删除同一把 New API Key"**替换为"门户 Key 生命周期本地管理，运行 Key 按用户 + New API 分组独立管理"。
4. **"门户价格仅继承门户分组对应的 New API 分组倍率"**替换为"门户按分组 + 模型配置折扣，发布时校验价格方向约束"。
5. **"New API 日志行 ID / 接口返回 id 可作请求标识"**替换为"必须捕获响应头真实请求 ID 并作唯一关联键"。

以下既有能力继续保留：

- 门户用户与 New API 用户的一一同步；
- 充值额度向对应 New API 用户等额同步（阶段一）及其幂等、失败分级、对账升级机制；
- 充值、扣费和补偿记录的幂等与审计要求。

### 13.3 迁移

项目尚未正式推广、无真实用户，迁移从简：

1. 存量测试性质的门户 Key 绑定（`newapi_key_binding`）与远端 token 全部作废清理，不做兼容收编。
2. 存量 `usage_log_snapshot` 明细快照（含坏 ID 数据）废弃；聚合快照中余额镜像保留（阶段一对账展示继续使用）。
3. `/v1` 流量在 Caddy/DNS 层切换到门户网关后，关闭用户直连 New API 数据面的路径（配合安全要求 11.4）。
4. 切换前后的请求标识不混淆：切换后账本一律以真实请求 ID 关联。

## 14. 验证标准

### 14.1 模型级分组映射

- 给定门户分组 `dev`，可将 `gpt-5.5` 映射至 New API `price-70`，同时将 `claude-sonnet` 映射至 `price-50`。
- 用户使用同一把绑定 `dev` 的门户 API Key 请求两个模型时，网关分别使用正确的 New API 分组、模型和运行 Key。
- 修改 `dev + gpt-5.5` 的 New API 分组后，新请求使用新路由，已开始请求仍按旧版本结算，其他模型不受影响。

### 14.2 Key 复用与隔离

- 同一用户在同一门户分组创建两把门户 Key，两者状态和审计相互独立，创建过程无远端调用。
- 两把门户 Key 请求同一个目标 New API 分组时，复用同一把"用户 + New API 分组"运行 Key。
- 禁用其中一把门户 Key 后，该 Key 立即不可用；另一把门户 Key 及共享运行 Key 继续可用。
- 用户被禁用后，其所有门户 Key 和全部 New API 运行 Key 都不可继续调用。

### 14.3 运行 Key 按需创建

- 新用户注册只创建或绑定 New API 用户，不产生任何运行 Key。
- 首次请求命中无运行 Key 的"用户 × 分组"时，请求路径内创建成功并完成转发；同组合并发首次请求最终只产生一把远端 Key。
- 远端创建失败时请求返回可重试错误，重试后成功；本地无残留半成品凭证记录。
- 模拟"远端创建成功、本地写回前崩溃"后，重试路径按稳定名称查询并收编已有远端 token，不产生第二把远端 Key。
- 路由发布不依赖任何凭证预置，发布后新分组的运行 Key 随请求陆续产生。
- 发布指向"不在 UserUsableGroups 内的分组"或"无白名单端点支持的模型"的路由被校验拒绝。
- **反向冒烟验收**：模型元数据声明支持 Responses，但目标分组内仅有不支持 Responses 的渠道时，逐渠道验证失败 → 路由不得发布、该模型不进入可调用目录；为该分组补充支持 Responses 的渠道并重跑验证后方可发布。
- **混合渠道验收**：同一分组内同时存在一个支持 Responses 和一个不支持 Responses 的启用渠道时，门禁必须失败（或先隔离不支持渠道再发布）；**不得因一次普通选路请求碰巧命中支持渠道而通过**。
- **验证失效验收**：已发布路由涉及的渠道发生启停/换绑分组/模型映射变更后，相关验证记录立即失效，模型在重新验证通过前退出可调用目录。

### 14.4 计费与余额

- 门户充值成功后，钱包账本记一条正向流水，且同一业务单只向 New API 用户增加一次等额额度（阶段一）。
- 请求扣费金额 = 锁定价格版本下的门户价 × 实际 usage（含 cache read/write、reasoning 等全维度）；与 New API quota 扣费按理论关系可核对。
- 门户钱包余额 ≤ 0 时新请求被网关拒绝；余额 > 0 放行（一期无预占）。
- 发布"门户价 < New API 价"的路由/价格配置被校验拒绝。
- **负余额场景**：余额仅剩最小单位时发起大 `max_tokens` 请求 → 放行且结算后余额为负、入账成功；随后的新请求被拒绝。
- **并发场景**：同用户并发请求数不超过风险占用上限时在余额临界处全部放行 → 全部原子入账（余额更负），无丢账、无重复扣费；超过上限的请求收到 429。
- **串行待回填场景**：连续请求均已结束但 usage 被屏蔽、全部进入 `pending_backfill` → 风险占用不释放，达到上限后下一请求被拒绝（429）；任一请求完成结算（`settled`）后对应槽位释放、新请求恢复放行。
- **原子准入临界并发场景**：风险占用为 9、上限为 10 时同时发起两个请求 → 最终只有一个成功进入 `open`，另一个收到 429；任意时刻持久化风险占用不超过 10。
- **多实例一致性场景**：在两个网关实例上重复上述临界并发测试，结果一致（占用不超上限）。
- **崩溃恢复场景**：原子准入成功后进程崩溃 → 重启后该槽位仍被占用并继续阻断超限请求；该请求完成结算后槽位只释放一次（重复终态处理被幂等拒绝）。
- **透支冻结场景**：负余额绝对值越过冻结阈值 → 用户被自动冻结、触发告警；管理员人工解冻后可恢复。
- **舍入场景**：单 token 级极小请求结算为 1 micro-USD（最小扣费）；连续大量小额请求逐笔 ceil 入账，总额与逐笔之和一致（无跨请求余数）；含 cache read/write 与 reasoning 的组合请求按互不重叠计费桶计价，OpenAI 系 `cached_tokens` 子集不被重复计费。
- **冲正场景与余额算例**：初始余额 `100`，请求扣费 `-30` 后余额 `70`，执行冲正写入 `+30`（绝对值等于原流水、符号相反、引用原流水 ID，不重算）后余额恢复 `100`；对同一原流水重复发起冲正被幂等拒绝。
- 同一真实请求 ID 重复结算被幂等拒绝，不产生重复扣费流水。
- 用量层对账：同一请求两侧 token 数一致。金额层对账：容差内一致或差异可解释。
- 制造一笔差异后，系统只告警并保留证据，不自动修改任意一侧余额；管理员可用有审计记录的人工补偿恢复一致。

### 14.5 请求追溯与回填

- 门户捕获并保存每次请求的 `X-Oneapi-Request-Id`（含失败请求）。
- 屏蔽响应 usage（模拟解析失败）后，账本经日志定点回填在秒级到分钟级内到达 `settled`，金额正确。
- 模拟"网关发出请求后崩溃"：先写的 `open` 记录存在；批量同步将远端日志匹配回该记录或记为 `orphan_remote`，消费金额不丢失。
- **正常路径追溯**：使用任一侧请求 ID，都能查到门户用户、门户 Key、门户分组、门户模型、New API 分组/模型、路由版本、价格版本、usage 与扣费。
- **孤儿路径追溯**：`orphan_remote` 记录可查到门户用户、New API 分组、运行 Key、模型、usage 与扣费；门户 Key 为空且被列入人工核查队列。
- 重复触发同一请求的日志回填/同步不产生重复账单（真实请求 ID 幂等约束生效）。
- Dashboard 请求明细来自门户账本；"计费中"状态请求在回填后自动补全费用。

### 14.6 安全与凭证边界

- 用户和浏览器无法获得 New API 运行 Key。
- 使用 Anthropic 原生 SDK（携带 `x-api-key`）经网关请求 `/v1/messages`：请求成功；抓包确认到达 New API 的请求中不含门户 Key 的任何载体，鉴权使用运行 Key。
- 绕过门户网关直接调用 New API 数据面会被网络或访问控制拒绝。
- 日志、错误与导出中不出现完整凭证明文。

## 16. 现状依据与实测记录

### 16.1 现状事实（2026-07-13 逐条核对代码确认）

- 门户用户与 New API 用户已具备一一同步绑定能力（`newapi_user_binding`，凭据加密存储）。
- 当前门户创建 Key 时，按门户分组解析单一 New API 分组、远端创建 token 并把**远端明文返回用户**，本地只存掩码；该行为由本需求的"本地门户 Key + 内部运行 Key"模式替代。

- 当前充值链路已包含等额增加 New API 额度、幂等（订单号唯一索引 + claim）、失败分级与 `reconciliation_required` 升级处理，阶段一继续复用。

### 16.3 New API 预占机制（源码结论，二期设计输入）

预扣公式（`relay/helper/price.go`）：`preConsumedTokens = max(promptTokens, 全局常量)`，客户端带 `max_tokens` 时累加；预扣额 = tokens × 模型倍率 × 分组倍率；阶梯计费下 `max_tokens` 缺省用 8192 兜底。生命周期（`service/billing_session.go`）：余额 ≤ 0 或不足预扣额拒绝 → 高余额触发信任旁路（跳过预扣、事后结算）→ 令牌/资金两步预扣（失败互回滚）→ 终态 `delta = 实际 − 预扣` 多退少补 → 失败异步全额退（幂等）。

已知缺陷（评估兜底可靠性时须知）：查扣无互斥的 TOCTOU 竞态可在高并发下透支（[issue #5690](https://github.com/QuantumNous/new-api/issues/5690)）；流式断连 `completion_tokens=0` 仍按 prompt 扣费（[#4168](https://github.com/QuantumNous/new-api/issues/4168)）；断连后 final usage 缺失可能全额退预扣（[#5235](https://github.com/QuantumNous/new-api/issues/5235)）。结论：New API 等额兜底在正常流量下可靠，不构成绝对硬闸；流式中断场景两侧扣费口径可能天然不一致，金额层对账容差需将此计入预期。

## 17. 二次评审结论（2026-07-13）

### 17.1 总体结论

本次评审认可以下总体方向：门户 API Key 与 New API 运行 Key 解耦、以“门户分组 + 门户模型 ID”执行模型级路由、门户建立第一方请求账本、使用 New API 真实请求 ID 回填 usage，以及阶段一保留双侧记账并进行对账。

但当前文档仍存在 3 个阻塞项、3 个重要缺口和 1 个分期问题，尚不适合作为“v2 定稿”直接进入详细设计。建议文档状态调整为：

> 需求决策已确认，方案存在阻塞项，待修订后进入详细设计。

以下问题解决前，本需求评审结论为：**有条件不通过**。

### 17.2 阻塞项（P0）

#### P0-1 `/v1/messages` 的鉴权凭证替换不完整

当前方案只要求替换外发请求的 `Authorization`。但 Anthropic 客户端通常使用 `x-api-key`；New API v1.0.0-rc.20 在 `/v1/messages` 和部分 `/v1/models` 请求中会读取 `x-api-key`，并用它覆盖 `Authorization`。如果网关保留用户传入的门户 Key，即使已经设置 New API 运行 Key，New API 最终仍可能使用门户 Key 鉴权，导致请求失败，同时把门户凭证继续传入下游。

修订要求：

1. 网关完成门户鉴权后，必须清理所有客户端凭证载体，再按目标端点注入 New API 运行凭证。
2. 一期至少覆盖 `Authorization` 和 `x-api-key`；未来扩展端点时同步评估 query key、`x-goog-api-key`、WebSocket protocol 等凭证载体。
3. 验收增加 Anthropic 原生 SDK 请求，确认门户 Key 不会传给 New API，运行 Key 能正常鉴权。

源码依据：[New API rc.20 `middleware/auth.go`](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/middleware/auth.go#L331-L336)。

#### P0-2 门户余额事实源、金额精度与入账原子性尚未确定

文档多次使用“门户账本余额”“门户扣费”“负向分录”等概念，但尚未明确用户余额的唯一事实源究竟是现有 `credit`、`apipool_ledger_entry`，还是新建的钱包账本。这不是物理表名问题，而是必须在需求阶段确定的业务不变量。

现状限制包括：

- `credit` 使用整数额度和 FIFO 消费，余额不足时直接失败，不能天然表达调用完成后的欠款；
- `apipool_ledger_entry` 当前主要记录向 New API 加额和人工调额，不是完整的钱包流水；
- 单次模型请求费用通常小于一美分，现有整数美分口径无法准确承载请求级计费；
- cache read、cache creation、Anthropic 5m/1h cache 等维度会改变实际计费，不能只保存 prompt/completion tokens。

修订要求：

1. 明确门户用户余额的唯一事实源及追加式账本语义。
2. 明确内部最小金额单位和舍入策略，例如统一使用整数 micro-USD 或等价高精度单位。
3. 明确充值、请求扣费、退款、人工调整如何进入同一余额闭合公式。
4. 请求账本结算与钱包扣费必须原子、幂等；同一真实请求 ID 不得重复扣费。
5. 价格版本必须包含所有实际计费维度及其倍率，不能只保存输入价和输出价。

#### P0-3 一期无预占时缺少超额消费后的结算规则

“门户账本余额 > 0 即放行”只能判断用户还有余额，不能证明余额足以支付本次请求。阶段一又允许门户价格高于目标 New API 价格，因此 New API 剩余余额可能显著高于门户余额，不能作为门户余额的等价硬闸。

例如，两侧初始余额均为 `$10`，门户价格为 New API 价格的两倍；当门户余额只剩 `$0.01` 时，New API 仍可能剩余约 `$5`。此时一个门户价格 `$1`、New API 价格 `$0.50` 的请求会被两侧放行，门户结算后应产生 `-$0.99` 余额。当前请求账本状态机没有负余额、欠款或结算失败状态，现有 `consumeCredits()` 也会因余额不足拒绝落账。

修订要求：一期必须明确选择以下路径之一：

1. 将请求级预占与精确拦截提前纳入一期；或
2. 明确允许调用后产生负余额，并定义最大透支边界、并发限制、负余额入账、后续请求阻断和人工处理规则。

无论选择哪条路径，验收必须增加“余额仅剩最小单位”“大 `max_tokens`”“同用户并发请求”和“结算金额大于请求前余额”等场景。New API 已知存在高并发透支窗口，不能将其描述为绝对可靠的硬闸，参见 [issue #5690](https://github.com/QuantumNous/new-api/issues/5690)。

### 17.3 重要缺口（P1）

#### P1-1 真实请求 ID 链路存在无法精确关联的崩溃窗口

正常路径中，New API 会全局生成 `X-Oneapi-Request-Id`，响应头与日志 `request_id` 可以精确关联；这一主链路成立。

但如果网关已把请求发给 New API，却在收到或持久化响应头前崩溃，则可能出现：New API 已产生消费和日志，门户账本却没有真实请求 ID。由于多把门户 Key 共享同一运行 Key，仅凭 New API 用户、运行 Key、模型和时间窗口不能保证精确还原到某一把门户 Key。因此，“每次请求都能通过真实请求 ID 关联到门户 API Key”的强保证在该窗口内并不成立。

修订要求：

1. 在发出任何 New API 请求前，先持久化门户请求账本 `open` 记录及 `remoteAttemptAt`。
2. 批量日志同步不仅处理已有 `pending_backfill`，还必须扫描 New API 中门户侧不存在的真实 request ID。
3. 增加 `orphan_remote` 或 `reconciliation_required` 状态，用于承接无法精确恢复到门户 Key 的远端消费。
4. 若业务坚持所有场景都必须精确关联到门户 Key，则需要验证 New API 能否持久化门户请求 ID；如需修改 New API，应同步调整本需求的非目标边界。

源码依据：[New API rc.20 `middleware/request-id.go`](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/middleware/request-id.go#L10-L18)。

#### P1-2 运行 Key 懒创建的分组权限和远端幂等前提未闭环

New API rc.20 只有在目标 token group 属于该用户的可用分组集合时才允许调用；否则推理请求返回 403。但 `POST /api/token/` 创建接口本身不会完成同等的可用分组校验，因此可能出现“运行 Key 创建成功，首次推理请求才失败”的情况。

当前第 16 节只验证了 token 能绑定单一分组，尚未验证同一普通用户可同时使用 `price-70`、`price-50` 等多个目标分组。路由发布前必须校验目标分组存在、倍率有效、模型可用，并属于同步用户的可用分组集合；或者建立所有门户同步用户统一使用某个基础 New API 用户组的明确不变量。

此外，New API 创建 token 不接受业务幂等键，token 名称也不是远端唯一约束。本地占位只能解决正常并发，不能解决“远端创建成功、本地写回前进程崩溃”。运行 Key 方案必须定义稳定且可重建的远端名称，并在重试前按稳定名称查询和收编已有远端 token；不能简单删除本地占位后再次创建。

源码依据：[New API rc.20 分组鉴权](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/middleware/auth.go#L420-L436)、[可用分组计算](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/service/group.go#L10-L36) 和 [`POST /api/token/` 实现](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/controller/token.go#L190-L233)。

#### P1-3 端点白名单与门户模型目录可能互相矛盾

一期明确不支持 `/v1/responses`、image 和 audio，但当前模型定价数据已经包含 Responses-only 和 image-only 模型；仓库测试中的 `gpt-5.5` 即声明为 `supported_endpoint_types: ['responses']`。如果 `/v1/models` 继续返回这些模型，用户会看到模型可用，但真实调用只能得到 404。

修订要求：

1. 路由发布前必须验证目标模型至少存在一个网关已支持的调用端点。
2. `/v1/models` 只能返回当前网关实际可调用的模型，或明确返回并展示端点能力。
3. 如果 `gpt-5.5` 等 Responses-only 模型属于一期必须售卖范围，则应把 Responses API 的 usage 行为 spike 和网关支持提前到一期。

### 17.4 实施分期问题（P2）

阶段①当前被描述为“直接解决 R-P1-7 分组重映射漂移”，但阶段①只有模型级路由表和运行 Key 池管理面。在阶段②网关数据面正式切换前，用户请求仍使用旧 New API Key，新的模型级路由不会参与真实调用，因此阶段①不能独立解决生产漂移。

建议将阶段①改为“数据结构与管理面基础”，并将阶段①与阶段②作为同一个不可拆分的上线门禁；或者直接合并为一个发布阶段。R-P1-7 只有在新网关接管 `/v1` 流量、旧 Key 作废且模型路由实际生效后才能关闭。

### 17.5 修订后复审门槛

重新提交评审前，文档至少需要补齐：

1. 门户钱包唯一事实源、金额单位、舍入和结算原子性。
2. 一期无预占情况下的负余额或透支处理决策。
3. 多协议鉴权头清理与替换规则。
4. 请求转发崩溃窗口和 orphan remote consumption 的恢复规则。
5. New API 多分组可用性及远端运行 Key 幂等恢复规则。
6. 模型目录与网关端点能力的一致性门禁。
7. 调整实施分期及对应验收标准。

完成以上修订后，再进入 `docs/design/portal-newapi-routing-billing-decoupling/` 产出详细设计。

### 19.2 阻塞项（P0）

#### P0-A 请求级金额舍入规则仍未定义

文档已经选择整数 micro-USD 作为钱包金额单位，但“计费单价 × token 数”仍可能产生不足 1 micro-USD 的小数结果。仅定义存储单位，不能自动确定：

- 在价格计算的哪一步舍入；
- 采用何种舍入模式；
- 输入、输出、cache read、cache write、reasoning 等维度是分别舍入还是合计后舍入；
- 小于最小单位的金额是直接丢弃、最小扣费，还是跨请求携带余数；
- 退款和冲正是否严格复用原扣费结果，避免二次计算产生差额。

此外，各协议 usage 的总量与明细字段可能存在包含关系。详细设计可以确定字段级公式，但需求必须先固定业务不变量：所有原始 usage 先归一化为互不重叠的计费桶，同一 token 不得因同时出现在总量和明细字段中被重复计费。

修订要求：在需求中明确唯一舍入点、舍入模式、子最小单位处理、冲正规则和计费桶不重复原则；验收增加单 token、连续大量小额请求、cache/reasoning 组合及原路冲正场景。

#### P0-B 最大透支边界和并发限制仍未定义

决策 9 写明“最大透支敞口 ≈ 单请求最大成本 × 用户并发数”，但当前方案既没有定义单请求最大可计费金额，也没有定义每用户并发硬上限，并同时声明监控告警不设硬限。两个乘数都没有上限时，该公式不能构成可执行的最大透支边界，监控也只能发现敞口，不能限制敞口。

修订要求：选择并明确以下一种口径：

1. 定义每用户并发硬上限、各端点/模型的单请求可计费上限，以及由此计算出的最坏透支金额；或
2. 明确一期接受“无业务硬上限”的资金风险，给出受基础设施容量和模型限制约束下的量化最坏估算、风险责任人及显式批准记录。

无论选择哪种口径，都应定义达到告警阈值后的自动阻断或降级动作；只写人工催缴/核销不足以构成事前风险控制。

### 19.3 重要缺口（P1）

#### P1-A 孤儿消费的门户 Key 归因口径前后冲突

7.5.2 已明确接受“归用户始终精确、归具体门户 API Key 尽力而为”的弱化边界，但以下内容仍保留无条件强保证：

- 3.1 产品目标要求通过真实请求 ID 关联到门户 API Key；
- 7.8 追溯语义未区分正常请求和 `orphan_remote`；
- 14.5 要求使用任一侧请求 ID 都能查到门户 Key 等完整信息。

这些要求在“请求已发往 New API、网关在捕获真实请求 ID 前崩溃且无法唯一匹配 open 记录”的场景下不可同时满足。

修订要求：统一改为分级保证——正常路径及可唯一恢复的请求必须精确归因到门户 Key；无法唯一匹配的 `orphan_remote` 必须精确归因到用户、New API 分组、运行 Key、模型、usage 和扣费，但门户 Key 允许为空并进入人工核查。14.5 应分别为两类路径设置验收。

#### P1-B Responses 渠道原生能力尚未形成发布门禁

16.2 已实测证明：相同 `/v1/responses` 请求经支持 Responses 的渠道成功，经不支持的渠道会透传上游错误。当前 7.2.7 的发布校验只检查“模型是否存在白名单端点”，不能证明目标 New API 分组中实际可能被选择的渠道支持该端点。因此仍可能出现“路由发布成功、模型进入目录、真实请求失败”。

修订要求：

1. 路由或渠道发布前，验证目标分组内所有可能承接该模型和端点的启用渠道均原生支持该端点；不能满足时，应通过分组/模型隔离避免选中不支持的渠道。
2. 若 New API 暂无可机器读取的渠道端点能力，则把“目标分组 + 模型 + 端点”的真实冒烟测试作为发布硬门禁，而不只是运营提示。
3. 14.3 增加反向验收：模型元数据声明支持 Responses，但目标分组只有不支持 Responses 的渠道时，路由不得发布、模型不得进入可调用目录。

2. 当前文档未通过 Prettier 格式检查，应在内容定稿后统一格式化。

### 19.5 再次复审门槛

再次提交评审前，至少需要完成：

1. 固定请求级金额舍入、子最小单位、冲正及计费桶去重规则。
2. 固定一期最大透支边界与并发限制，或形成无硬上限风险的量化批准记录。
3. 统一正常请求与 `orphan_remote` 的门户 Key 归因承诺和验收口径。
4. 将 Responses 等端点的真实渠道能力纳入路由/渠道发布硬门禁和反向验收。
5. 修正文档编号并通过格式检查。

### 21.2 阻塞项（P0）

#### P0-B 待回填消费未纳入透支风险占用

决策 15 将并发硬上限定为“同一用户同时进行中的网关请求数”，7.5.2 也只在请求入口检查进行中请求数。但请求已经结束、响应 usage 未解析成功时，会进入 `pending_backfill`：此时远端可能已经消费，门户尚未扣费，钱包余额和透支冻结阈值都不会变化，而该请求很可能已经释放并发槽位。

因此用户可以串行制造“请求结束但仍待回填”的消费，并在日志回填前继续发起新请求。实际未结算敞口可能持续累积，不能再由“并发上限 × 单请求最坏成本”约束。负余额超过阈值后的自动冻结属于结算后的事后动作，也无法阻止这一窗口继续扩大。

修订要求：

1. 将每用户风险占用定义为所有“可能已经产生远端消费但尚未确定结算金额”的请求，而不只是网络层仍在进行的请求；至少覆盖 `open`、`pending_backfill` 及未决的孤儿消费。
2. 风险槽位只能在请求进入 `settled`，或明确确认未产生消费的 `failed_unbilled` 后释放。进入 `unbilled` 或无法确定金额的异常状态时，必须保持风险占用或直接冻结用户，直到人工处理完成。
3. 达到风险占用上限后，新请求 fail-closed 返回 429；批量日志同步和人工处理不得绕过该状态。
4. 各白名单模型的单请求最坏成本记录必须成为路由发布前置条件；缺少记录、记录过期或模型上下文/最大输出配置变化时，不得发布或继续展示为可调用。
5. 验收增加串行场景：连续请求均结束但 usage 被屏蔽、全部进入 `pending_backfill`，达到风险槽位上限后下一请求必须被拒绝；任一请求完成结算后才释放对应槽位。

#### P0-C 冲正流水符号与钱包账本约定冲突

钱包账本已经定义请求扣费为负向流水，并要求冲正使用反向流水。因此一笔请求扣费 `-C` 的冲正必须是 `+C`。但决策 16 写成“退款与冲正……负向流水关联原流水 ID”，14.4 的冲正验收也要求“负向流水金额与原流水严格相等”。若按字面实现，会在原扣费后再写一笔负数，形成二次扣费，而不是冲正。

同时，“未消费余额退款”和“请求扣费冲正”是两类方向不同的业务动作，不应共用含糊的“负向流水”表述。

修订要求：

1. 明确采用带符号金额，并固定示例：充值 `+C`、请求扣费 `-C`、请求扣费冲正 `+C`、未消费余额退款/提现 `-C`、充值退款或充值冲正 `-C`。
2. 任意冲正流水的绝对值必须等于原流水，符号必须与原流水相反，并通过原流水 ID 建立唯一关联；同一原流水不得被重复冲正。
3. 将决策 16 和 14.4 中“负向流水”的表述改为“与原流水符号相反的冲正流水”。
4. 验收增加余额算例：初始余额 `100`，请求扣费 `-30` 后余额 `70`，冲正 `+30` 后必须恢复为 `100`；重复冲正必须被幂等拒绝。

### 21.3 重要缺口（P1）

#### P1-B 分组级单次冒烟不能证明所有候选渠道可用

7.2.7 当前对“目标分组 + 模型 + 端点”执行一次最小真实调用。New API 仍负责在该分组内选择具体渠道；当同一分组中同时存在支持和不支持 Responses 的渠道时，一次冒烟可能恰好命中支持渠道并成功，但后续请求、重试或故障切换仍可能选中不支持渠道。

因此，单次分组级冒烟只能证明“至少有一个当时被选中的渠道成功”，不能证明“所有可能承接该端点的渠道均可用”，也不能支撑 `/v1/models` 所承诺的稳定可调用语义。

修订要求：

1. 对目标分组内每个可能承接该“模型 + 端点”的启用渠道分别执行可归因到具体渠道的冒烟；验证证据至少记录渠道 ID、模型、端点、配置版本和验证时间。
2. 如果 New API 暂时不能把冒烟请求固定到具体渠道，则必须通过临时隔离、专用测试分组或逐渠道测试接口完成验证；不能用一次普通选路请求代替全渠道验证。
3. 路由发布只能引用全部验证通过的渠道集合。渠道新增、启停、换绑分组、模型映射或协议配置变化后，相关验证立即失效，重新验证前路由不得继续承诺该端点可用。
4. 验收增加混合渠道场景：同一分组同时存在一个支持 Responses 和一个不支持 Responses 的渠道时，门禁必须失败或先隔离不支持渠道；不得因一次请求命中支持渠道而通过。

### 21.4 再次复审门槛

再次提交评审前，至少需要完成：

1. 将待回填和其他未决消费纳入每用户风险占用，并为异常终态定义 fail-closed 行为。
2. 将逐模型单请求最坏成本记录提升为路由发布硬门禁，并补充配置变化后的失效规则。
3. 统一请求扣费、冲正、退款和充值退款的有符号流水方向及幂等关系。
4. 将分组级一次冒烟升级为覆盖每个候选渠道的可归因验证，补充混合渠道反向验收。

## 24. 五次复审结论（2026-07-13）

### 24.1 总体结论

v5 已经关闭第 21 节的三项 finding：

- `open`、`pending_backfill`、未决 `orphan_remote` 与 `unbilled` 的风险占用/冻结语义已经补齐；
- 逐模型单请求最坏成本已经成为路由发布门禁；
- 请求扣费、冲正和退款的流水方向已经明确；
- 分组级冒烟已经升级为逐候选渠道的可归因验证，并补充混合渠道与配置失效验收。

但请求准入流程仍存在一个具有现实并发触发路径的新增 P0：风险占用上限目前只有“检查”语义，没有定义原子“检查并占用”，实际并发下仍可突破硬限。该问题符合第 23 节规定的新增 P0 阻塞标准。另有一处带符号流水公式的 P1 一致性问题。

因此，本次复审结论为：**有条件不通过；修复 P0-D 后即可冻结需求并进入详细设计**。P1-C 不单独触发下一轮评审，但应在冻结前顺手消除歧义，或明确进入第 15 节作为设计输入。

### 24.2 阻塞项（P0）

#### P0-D 风险槽位的检查与占用不是原子准入操作

7.5.2 当前流程为：

1. 步骤 4 读取用户未决消费计数，未达到上限则放行；
2. 步骤 5 取得或创建运行 Key；
3. 步骤 6 才创建计入风险占用的 `open` 请求记录。

“检查当前计数”和“创建 `open` 记录占用槽位”之间存在时间窗口。现实触发路径如下：风险占用上限为 10，用户当前已有 9 个槽位；两个并发请求 A、B 都在步骤 4 读到 9，因此都通过；随后 A、B 分别创建 `open` 记录，最终风险占用变为 11。此时系统已经突破硬上限，“风险占用上限 × 单请求最坏成本”的最坏敞口公式不再成立。

该问题不是物理表或锁实现的设计细节，而是资金风险门禁必须满足的业务不变量：任何时刻，成功取得风险槽位的未决消费数量都不得超过配置上限。

修订要求：

1. 将“校验风险上限 + 获取一个风险槽位 + 持久化对应请求记录”定义为一个跨进程、跨实例的原子准入操作；普通的“先查询计数、后插入记录”不满足要求。
2. 只有成功取得持久化风险槽位的请求才允许向 New API 发起推理调用；未取得槽位必须 fail-closed 返回 429。
3. 建议在运行 Key 已取得后、发出任何推理请求前执行原子准入，避免运行 Key 懒创建失败长期占用风险槽位；具体事务、锁或原子计数实现留到详细设计确定。
4. 请求进入 `settled` 或确认无消费的 `failed_unbilled` 时，状态迁移与槽位释放必须原子完成；重复终态处理不得重复释放槽位。
5. 风险占用必须以持久化状态为事实源，服务重启或多实例切换后可以从请求账本重建；不得仅依赖单进程内存计数。
6. 原子准入失败、进程崩溃或运行 Key 创建失败时，必须保证不会出现“已发出推理但没有风险槽位”或“永久占槽但没有对应请求记录”的半成品状态。

验收要求：

- 风险占用为 9、上限为 10 时，同时发起两个请求，最终只能有一个请求成功进入 `open`，另一个必须收到 429；任意时刻持久化风险占用不得超过 10。
- 在两个网关实例上重复上述并发测试，结果必须一致。
- 模拟准入成功后进程崩溃，重启后风险槽位仍存在且继续阻断超限请求；完成结算后只释放一次。

### 24.3 非阻塞一致性问题（P1）

#### P1-C 带符号流水与余额闭合公式仍有二次取反歧义

决策 13 已明确流水金额带符号：充值为正，请求扣费、未消费余额退款和充值退款为负，请求扣费冲正为正。但 7.7 仍同时写出：

```text
期初 + 充值 − 扣费 − 退款 ± 调整 = 期末
```

如果“扣费”和“退款”直接代入账本中的带符号金额，该公式会对负数再次取反，与“余额 = 流水之和”的定义冲突。

修订要求：将唯一闭合公式统一为：

```text
期末余额 = 期初余额 + Σ 本期流水 signedAmount
```

如果文档仍需展示按业务类型展开的公式，必须明确其中“扣费”和“退款”使用非负绝对值，而不是账本字段中的带符号金额。

该问题已有决策 13 的明确方向，不影响整体架构，按第 23 节规则不单独阻塞需求冻结；但建议与 P0-D 同一修订中消除，避免冻结后的需求基线存在两套可冲突的计算表达。

### 24.4 冻结门槛

本轮后不再要求扩展需求范围。冻结前只需完成：

1. 明确风险槽位的原子准入与原子释放不变量，并增加临界并发、多实例和崩溃恢复验收。
2. 将余额闭合公式统一为带符号流水求和口径。
