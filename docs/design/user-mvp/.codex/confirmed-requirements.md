# user-mvp 已确认需求与约束（阶段 0 固化）

> 来源：`docs/08-user-mvp-requirements.md` 全文 + 2026-06-24 与用户的 4 项澄清 + 客观代码现状。
> 这是设计地基，DESIGN.md 各节不得与此冲突。

## 0. 设计方式（用户澄清 Q1）

- **基于 docs/08 需求 + 真实代码现状独立推导设计**，不照搬历史临时 plan（`~/.claude/plans/*` 不作为设计来源）。DESIGN.md 须自包含、可进仓库。
- 注意：本文件中的需求/约束均来自 docs/08 与用户拍板，**不是**从历史 plan 抄来的方案；数据模型、表结构、改动方案要由 Author 从需求与现状自行推导（允许、且应当给出更优解）。

## 1. 目标

让真实用户完成完整自助闭环：
`注册/登录 → 在线充值或管理员发放额度 → 查看模型与价格 → 选分组创建 API Key → 真实调用模型 → 控制台看到余额、用量与 Key 状态`。
同时保留管理员手动调额（充值/补偿/扣减/异常处理）。

## 2. 本次范围（做什么）

1. **模型/供应商/分组/能力/价格/状态体系**：把当前硬编码的模型目录搬到数据库 + 后台 CRUD；`/models` 支持「供应商 → 分组 → 能力 → 状态」四层筛选（四层均控制台可配）；**同一 modelId 在不同分组 = 不同售卖项、可有不同价/折扣/状态/说明**。
2. **建 Key 选分组**：用户建 Key 必须选分组；门户分组 ↔ 后台网关（New API）group 的映射可由管理员配置；建 Key 时**展示该分组下可用模型范围**；邮箱是否验证**不作为建 Key 门槛**。
3. **在线支付落地（澄清 Q2 = 配置化 + 验证 + 补展示缺口）**：不重写支付核心；以「接回设置页填密钥 + 端到端跑通 + 补齐 dashboard 充值记录『订单时间/金额/支付状态/到账状态/到账处理中』展示」为主。
4. **管理员额度运营（澄清 Q4 = 补只读查看 + 复用已有 retry）**：沿用已有 adjust-quota 增减；**新增用户详情聚合只读视图**（余额/用量/API Key/额度调整历史）；异常处理复用现有 retry/reconciliation API。每次调额记录操作人/目标用户/金额/原因/时间（已有 ledger + audit log）。
5. **登录增强**：接回 admin 设置页（OAuth/Resend/验证开关的统一配置入口，当前是 redirect 桩）；Google/GitHub OAuth 配置化（代码已就绪，只差填密钥）；邮箱**链接验证**（非 OTP）；邮件**只用现成 Resend，不做 SMTP**；三种登录后用户权益一致。
6. **完整 dashboard 自助闭环**：在已实现基础上补齐——余额/额度展示、最近用量概览、API Base URL、充值/建 Key/查用量入口、Key 列表加分组列、余额不足提示、调用后余额用量变化可见。

## 3. 建 Key 与模型范围的取舍（澄清 Q3，已拍板）

- 建 Key **只绑分组**（把分组翻译成 New API group 写入 token），**不限定具体 allowedModels**。
- 「该分组下可用模型范围」做成**展示性信息**（创建时列出该分组当前可调模型，不写进 token）。
- 「已下线模型若影响已有 Key」**降级**为 `/models` 与 dashboard 的**状态标注**，不做 Key 级精确受影响分析。

## 4. 关键架构约束（硬性）

- **New API 无「读取分组/模型/价格列表」接口** → 模型目录、分组、价格由门户自维护一份，管理员在门户与网关两侧**手动对齐**，**本版本不做两者自动同步**。
- **控制面/数据面分离（已有，不破坏）**：控制面 = 浏览器 → 门户 → bridge（内部 `NEWAPI_BASE_URL`）→ New API 管理接口；数据面 = 用户 `sk-key` → New API `/v1`，门户不在推理路径。
- **不向普通用户暴露**后台网关名称、后台网关管理入口或内部 ID；公共页面（`/models` 等）不得出现「New API」「group」等后台痕迹（守护测试 `tests/public-content/locale-copy.test.ts`）。
- quota 整数 `500000 = $1`；New API 无幂等 header，幂等靠门户 `ledger.orderNo` 唯一索引。
- 字典/配置走 DB（`config` 表 key-value + drizzle schema），admin 改后 `revalidateTag`。

## 5. 非目标（不做，划清边界）

docs/08 第 5 节 + 本轮澄清：
- 不把 `/docs` 快速接入文档作为本阶段紧迫项；不做邮箱验证码（OTP）输入流程；不做模型独立详情页；不做 Playground；不做团队/组织账户；不做用量导出；不做复杂发票/营销系统；不做老用户资产迁移；不暴露后台网关名称/入口/内部 ID。
- 支付：不重写支付核心、不做动态套餐管理后台（套餐仍可暂留 i18n）。
- 额度运营：不做独立异常仪表板、批量重试工具、失败告警。
- 建 Key：不做模型级精确限定、不做 Key 级受影响精确分析。
- dashboard 实时刷新：不做自动轮询/WebSocket（接受 SSR + 手动刷新；可加手动刷新按钮）。

## 6. 非功能需求

- **权限**：所有 admin 操作走 RBAC `requirePermission`；模型目录 CRUD 需新增 CATALOG 类权限并授权 admin。
- **兼容/迁移**：模型目录由硬编码迁到 DB 需 seed/迁移脚本；迁移沿用现有 `deploy/entrypoint.sh` 运行时 migrator，不改 Dockerfile/entrypoint。
- **DB 方言策略（2026-06-24 第 1 轮评审后由 Orchestrator 拍板，澄清原措辞）**：本仓库 barrel `src/config/db/schema.ts` 仅 `export * from './schema.sqlite'`，既有 bridge/业务表（`newApiKeyBinding`/`apipoolLedgerEntry` 等）本就只在 `schema.sqlite.ts` 定义，postgres/mysql 文件不含。新增的 `catalog_*` 表**遵循同一先例：只写进 `schema.sqlite.ts`（sqlite-only）**，不在 pg/mysql 文件补半套。「三方言不漂移」的可执行含义 = 类型从 sqlite barrel **单源推导、不分裂**；设计须给出守护（禁止运行时/类型路径 import pg/mysql 的 catalog 表，或加构建/类型断言证明单源）。生产仅 SQLite，pg/mysql 不在 user-mvp 支持面。**此为定稿决策，不是未决问题。**
- **可观测/审计**：额度调整与加额走 `apipoolLedgerEntry` + `newApiBridgeAuditLog`。
- **i18n**：新增页面、动态 label、sidebar 均需 en/zh 两套文案。

## 7. 验收标准（docs/08 第 4 节，逐条）

**用户验收**：① Google/GitHub/邮箱注册登录均可完成；② 邮箱注册收到验证链接；③ 已登录用户建 Key 不因邮箱未验证被阻止；④ 在线充值并看到余额变化；⑤ `/models` 找到≥1 个可用模型；⑥ 选分组建 Key；⑦ 复制 Key 并真实调用≥1 个模型成功；⑧ 调用后 dashboard 看到余额减少与用量记录；⑨ 禁用 Key 后该 Key 不能继续调用。

**管理员验收**：① 新增供应商/分组/能力/模型；② 同一 modelId 出现在不同分组并配不同价；③ 配置门户分组↔后台网关分组对应关系；④ 把模型从「即将上线」改「可用」并让用户建 Key 后调用；⑤ 下线模型或分组并让用户侧看到明确状态；⑥ 配置 Google/GitHub 与邮箱链接验证；⑦ 查看支付订单与到账状态；⑧ 对用户额度增加与扣减；⑨ 查看额度调整记录与用户用量。

## 8. 默认假设（docs/08 第 6 节）

在线支付进入本版本；管理员额度可增可减；分组是用户可感知的价格/渠道选择；同一 modelId 在不同分组视为不同售卖项；New API 不提供读分组/模型/价格接口（门户自维护、手动对齐、不自动同步）；首批至少 1 分组 + 1 供应商 + 1 模型完成真实调用验证；邮箱沿用链接验证；邮箱链接验证不作为建 Key 门槛。
