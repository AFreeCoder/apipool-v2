## 0. 评审方法

本轮按用户指定流程执行：

1. 使用 `superpowers:brainstorming` 先读需求文档，评审需求完整性和关键缺口，不进入业务代码开发。
2. 使用 `gstack:autoplan` 的四阶段视角复评设计：CEO/产品范围、Design/体验、Engineering/架构、DX/开发者体验。
3. 将评审意见分为“必须修改 / 建议修改 / 可暂缓”。
4. 修订 `DESIGN.md`，并把最终设计拆为可执行计划。

本轮只修改设计、评审和计划文档，不修改业务代码。

## 1. 需求完整性评审

### 1.1 结论

需求文档已经可以作为 user-mvp 的产品基线。它明确了版本目标、用户闭环、管理员闭环、非目标、状态基线和外部依赖验收。

本轮未发现需要阻塞设计推进的需求缺口；但发现若不写进设计，会导致实现或验收漂移的关键假设。

## 2. gstack:autoplan 四阶段评审

### 2.1 CEO / 产品范围评审

评分：8/10，修订后可进入计划拆解。

必须修改：

- 旧设计仍带“2026-06-24 已冻结”语气，与 2026-06-26 需求基线冲突。
- 旧设计更像开发前计划，没有说明当前实现已经覆盖的能力和剩余验收责任。
- 旧设计没有把“支付成功但未到账”的用户承诺和管理员救援责任讲清。

处理结果：

- `DESIGN.md` 改为“2026-06-26 需求基线修订版”。
- 新增 §2 当前实现校准，避免重复做已完成实现，也避免忽略仍需验收的状态。
- 新增 §7.2 支付与额度状态流，明确 pending/applied/failed 的用户和管理员含义。

建议修改：

- 把 user-mvp 目标写成用户闭环和管理员闭环，而不是按模块堆列表。
- 把 12 个月方向从实现计划中隔离，防止本轮 scope creep。

处理结果：

- 已在 `DESIGN.md` §1、§12 写入。

可暂缓：

- 自动化告警平台、分组自检、完整路由 fallback 仍不进入 user-mvp。

### 2.2 Design / 体验评审

评分：7/10，修订后可验收。

必须修改：

- 用户可见 Key 状态要从内部状态映射为简单状态，不应让用户理解 `failed_retriable` 等内部名。
- 用量同步状态要有清晰文案：同步中、暂无用量、数据可能延迟、同步失败。
- 账单页必须同时展示支付状态和到账状态，避免“已支付但余额没变”的体验断裂。
- 后台 raw i18n key 需要进入真实浏览器验收清单，不能只靠静态文件检查。

处理结果：

- `DESIGN.md` §7.1 写入内部状态到用户文案映射。
- `DESIGN.md` §7.3 写入用量状态表。
- `DESIGN.md` §7.2 写入账单状态展示规则。
- `DESIGN.md` §10.3 写入真实浏览器截图验收，覆盖 `/admin/catalog/*` 和设置页。

建议修改：

- `/models` 展示维度应补分类，不只供应商/分组/能力/状态。
- Key 列表应展示分组和可调模型范围，但继续声明这不是模型级授权。

处理结果：

- 已在 `DESIGN.md` §4、§6、§11 写入。

可暂缓：

- 更复杂的空态插画、营销式说明、Playground 引导不进入 user-mvp。

### 2.3 Engineering / 架构评审

评分：8/10，修订后可执行。

必须修改：

- 数据模型要和当前 sqlite schema 对齐，尤其是 `catalog_category`、`usage_snapshot.inputTokens/outputTokens`、`newapi_key_binding` 失败态字段。
- Key 状态流要覆盖“远端成功、本地保存失败”和 cleanup。
- 用量明细需要避免重复远端 request id 造成列表 key 和统计重复。
- 公共目录查询必须把 `newapiGroup` 和内部 id 隔离到服务端。

处理结果：

- `DESIGN.md` §6 按当前 schema 重写数据模型。
- `DESIGN.md` §7.1 写入 `remote_created_binding_failed` 和 cleanup。
- `DESIGN.md` §7.3 写入替换式刷新和列表 key 风险。
- `DESIGN.md` §5.2、§6.1 写入公共查询边界。

建议修改：

- 将 `amountUsd` 的美元数值单位写入设计，避免再次出现 cents/USD 混淆。
- 将 smoke 命令和 live 环境变量写入发布证据。

处理结果：

- 已在 `DESIGN.md` §6.3、§10.2、§11.3 写入。

可暂缓：

- 自动迁移到 postgres/mysql、自动对账 worker、独立告警平台暂不进入本轮。

### 2.4 DX / 开发者体验评审

评分：7/10，修订后可交付。

这里的“开发者”包括两类：使用 APIPool API 的终端用户，以及继续开发 user-mvp 的工程师。

必须修改：

- 终端用户第一次成功调用路径需要明确：API Base URL、分组建 Key、完整 Key 一次性展示、调用后用量可见。
- 实施计划需要从旧 dev-iteration 交接稿改为可执行计划，包含文件、测试、验收命令。
- 发布前不能只说单测通过，必须加入浏览器 dogfood 和截图。

处理结果：

- `DESIGN.md` §4.2、§10、§11 写入终端用户第一次成功调用路径和验收。
- `PLAN.md` 已按 `superpowers:writing-plans` 的执行结构重写。
- `docs/superpowers/plans/2026-06-26-user-mvp-refresh.md` 提供标准计划路径。

建议修改：

- 计划应把“已实现但需回归验证”和“需要补齐的开发项”分开，避免重复开发。
- 每个 UI step 都要有真实浏览器验收项。

处理结果：

- 已在 `PLAN.md` 中分为文档对齐、实现核查、测试回归、浏览器验收、发布证据。

可暂缓：

- 面向外部开发者的完整 `/docs`、SDK、迁移指南不进入 user-mvp。
