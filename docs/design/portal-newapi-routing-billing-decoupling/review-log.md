## 19. Codex 设计评审结论（2026-07-13）

> **评审结论：NO-GO / needs-revision。** 当前版本包含 3 个 P0 阻塞项、5 个 P1 重要缺口和 1 个 P2 文档一致性问题，不建议据此进入实施计划或编码阶段。
>
> 评审范围包括本设计、对应需求、现有 New API 客户端与门户绑定实现，以及相关备份恢复设计。本节只追加评审意见，不回写或替换前文，便于保留评审历史。

### 19.1 阻塞项（P0）

#### P0-1：运行 Key 生命周期按当前表结构和流程无法闭环

**问题与证据：**

- §3.3 将 `remote_name` 设为稳定名 `rk_{sha256(userId:group)[:24]}`，同时存在全局唯一约束和覆盖 `pending`、`active`、`rotating` 的部分唯一约束。
- §6.3 的失败路径把占位行更新为 `failed`，重试时再插入同一 `remote_name`；全局唯一约束会使重试继续冲突。
- 进程若在远端创建成功、本地回写前崩溃，本地会永久留下 `pending`；当前设计没有 pending 租约、超时接管或远端对账恢复机制，后续请求只能持续等待后返回 503。
- §6.4 先把旧 Key 标为 `rotating`，再以相同稳定名插入新 `pending`，会直接命中部分唯一约束。现有 `NewApiClient.createKey()` 又会按相同 `remote_name` 收编旧 token，因此即使绕过本地冲突，也不能形成真正的新旧 Key 轮换。

**影响：** 首次创建失败、进程崩溃、Key 失效和主动轮换都可能把某个 `(portal_user_id, newapi_group)` 永久卡死；这是数据面不可恢复故障。

**必须修改：** 选择并完整设计一种可执行模型：

1. 单行状态机：复用同一绑定行，以 CAS、generation 和租约实现创建、接管、失效及轮换；或
2. 版本化远端名：每代 Key 使用不同确定性名称，并用独立 current pointer 指向当前代。

两种方案都必须定义远端已成功但本地未知时的幂等收敛、旧 Key 撤销顺序、并发创建的唯一赢家，以及 stale pending 的超时接管规则。复审前至少补齐正常失败重试、远端成功后本地崩溃、并发首建、失效重建和主动轮换测试。

#### P0-2：无响应头不能证明上游未消费，当前分类会提前释放风险槽位

**问题与证据：** §4.4 把“原生 fetch 在响应头前抛错且没有 request ID”归类为“确认未消费”，随后进入 `failed_unbilled` 并释放风险占用。该推断不成立：请求可能已被 New API 接收并产生用量，只是连接在响应头返回前被重置。此时稍后的日志回填仍可能发现实际消费。

另一个关联缺口是：当前响应解析路径可在取得 usage 时直接结算，但没有把 `newapi_request_id` 明确列为结算前置条件。若响应包含 usage 却缺少 request ID，先行扣款后，批量同步或孤儿扫描再次发现同一远端请求时存在重复扣费或无法可靠归并的风险。

**影响：** 不确定结果被误判为零消费会低估风险敞口；缺失 request ID 的提前结算又会破坏远端日志关联和全局幂等。

**必须修改：**

- 只要请求已经向上游发出，且没有远端日志等明确证据证明未消费，就必须保持 `unknown` / `pending_backfill` 等仍占用风险额度的状态；网络异常本身不能进入 `failed_unbilled`。
- 明确 `newapi_request_id` 与结算的关系。若没有 ID，应先保存可用 usage 证据但不得形成不可关联的最终扣款，直到通过安全匹配补齐 ID 或采用另一种能够证明全局幂等的关联键。
- 增加“上游已消费后 socket reset”“响应有 usage 但无 request ID”“延迟日志随后出现”三类竞态测试，验证不提前释放槽位且不重复扣费。

#### P0-3：需求规定的备份恢复前置门禁没有进入本设计实施阶段

**问题与证据：** 对应需求明确要求：新增钱包、路由和凭证数据的备份恢复边界必须由独立 feature 定义并完成，之后才能实施本 feature。当前 `docs/design/release-backup-hardening/DESIGN.md` 仍标记为“待调整”，并明确真实恢复尚未得到证明；但本设计 §13 从建表、钱包双写直接进入迁移和切流，没有外部依赖门禁。

**影响：** 一旦钱包成为余额事实源、运行 Key 仅在本地加密保存，而备份与恢复没有覆盖并实测，新数据可能在故障时不可恢复；这不是上线后可补的普通运维项。

**必须修改：** 在阶段 1 之前加入不可绕过的前置门禁，至少包括：

1. 备份设计已按本 feature 的最终 schema 重新冻结；
2. 钱包流水/物化余额、请求账本、价格版本、运行 Key 密文及解密依赖、绑定和任务租约等对象均有明确备份边界；
3. 备份实现已完成，并以真实恢复演练验证数据可读、Key 可解密、钱包守恒和账本幂等不变量；
4. 恢复演练证据进入发布门禁后，才允许启动钱包迁移和数据面切流。

### 19.2 重要缺口（P1）

#### P1-1：运行 Key 懒创建会反复修改 New API 用户主分组

§6.3 以目标运行分组调用 `ensurePortalUserBinding()`。现有实现会进一步调用 `ensureUserGroup()`，通过 `PUT /api/user/` 把用户主分组改成目标分组。同一门户用户可能同时使用多个运行分组，并发首次请求会造成主分组 last-write-wins 抖动；而跨分组创建 token 已可由 `UserUsableGroups` 支持，没有必要为每把 Key 修改用户主分组。

**要求：** 绑定保证只负责用户存在且启用，不随请求修改主分组；运行分组只传给 `createKey()`。如果系统仍需要主分组，必须选择一个稳定基准值，并补充多分组并发首建测试。

#### P1-2：原生 fetch + `ReadableStream.tee()` 不满足透明且有界的代理要求

§4.4 的 tee 旁路对慢消费者没有可靠的总缓冲上限；1 MB SSE event 限制只约束解析器的单事件大小，不能限制 tee 为较慢分支累计的队列，因此长流或慢客户端可能把整个响应持续堆在门户进程内。

此外，评审时在 Node.js `v22.21.1` 上复现：原生 fetch 会自动解压 gzip 响应体，但仍可保留上游的 `content-encoding: gzip` 和压缩前对应的 `content-length` 头。若按设计直接复制响应头，客户端会收到“已解压 body + gzip/旧长度头”的损坏响应。

**要求：** 改为具备背压的 TransformStream/tap，或采用可保持原始字节语义的 HTTP 客户端；同时明确 `Accept-Encoding: identity` 策略，或在自动解压时清理 `content-encoding`、`content-length` 等不再成立的头。集成测试至少覆盖慢客户端、压缩上游、超长 SSE、客户端取消和解析支路异常。

#### P1-3：批量同步可能抢先结算仍在进行的 `open` 流式请求

§7.2 允许批量同步命中 `pending_backfill/open` 后直接结算。长流请求可能仍处于 `open`，批量日志先返回阶段性或降级后的 usage 并完成结算，随后响应解析器取得更完整 usage 时会被幂等终态挡住，最终按不完整数据扣费。

**要求：** 批量任务只能处理 `pending_backfill`，或处理已超过明确流所有权/完成超时的 `open`；应增加 owner lease、stream-finished 标记或等价状态约束。补充“长流仍在输出时批量日志先出现”的竞态测试，并规定丰富证据覆盖较弱证据的合并规则。

#### P1-4：cache 计费仍未满足“门户价格不低于 New API 实际价格”的硬边界

§3.8 的最坏情况风险公式只取 `max(input, cacheWrite5m, cacheWrite1h)`，漏掉 cached input/read 价格。价格由运营录入且设计没有数据库约束保证 cached input 一定不高于 input，因此公式在合法配置下可能低估最大敞口。

§5.3 同时承认 cache 方向校验只是结构性近似，依赖事后对账发现反向；这不能证明发布时已经满足需求中的硬门禁。金额对账是止损手段，不是价格发布前的证明。

**要求：** 风险上界纳入所有可能的输入侧价格桶；为 cache 维度取得权威 New API 计价比例或可审计的实际日志证据。无法确认时使用保守上界并拒绝发布，而不是仅依赖事后告警。补充异常 cache 价格、未知比例和最坏 token 组合测试。

#### P1-5：渠道验证失效后的路由语义前后矛盾

§2.3 和 §9.3 一方面要求请求解析时渠道验证仍在新鲜期，另一方面又写“失效后目录收缩，但后续请求不阻断”。两者会使实现无法确定：用户若直接携带旧模型 ID，验证失效后究竟应拒绝还是继续路由。

**要求：** 固化为单一规则并区分“新请求”与“已在途请求”。按需求约束，建议验证失效后从目录移除且所有后续新请求停止路由，已建立的在途调用不强制中断；重新验证通过后再恢复。必须增加旧模型 ID 直调、目录缓存命中和在途流三类测试。

### 19.3 文档一致性问题（P2）

#### P2-1：“定稿候选”与“本设计冻结”状态冲突

文档头部状态是“设计定稿候选（待评审）”，§18 却声明“本设计冻结”并把这些结论直接作为实施输入。在上述 P0/P1 未关闭前，这会误导后续计划或第三方评审，把候选假设当成已确认决策。

**要求：** 修订期间把 §18 改为“拟冻结结论”或等价措辞；只有复审通过后再统一更新文档状态和冻结声明。尤其需要同步修正 §18 中关于“运行 Key 失败清理不留半成品”“cache 硬方向校验”和“渠道失效后不阻断”的表述，使其与最终机制一致。

### 19.4 再次提交评审的最低门槛

1. 运行 Key 状态机能够覆盖失败、崩溃接管、失效和轮换，并有数据库约束与并发测试证明可执行。
2. 所有已发出但结果不确定的请求继续占用风险额度；结算具备可关联的远端 ID 或等价全局幂等证明。
3. 备份恢复 feature 完成重新设计、实现和真实恢复演练，并作为本 feature 实施前置门禁。
4. 关闭上述 5 个 P1 缺口，补齐慢流/压缩、批量竞态、cache 最坏边界和渠道失效测试。
5. 统一候选、冻结、阶段计划和 §18 摘要的状态表达；在此之前，本版本不应作为实施计划或编码输入。

### 21.2 阻塞项（P0）

#### R2-P0-1：日志无匹配仍不能证明未消费，120min 后释放槽位继续违反风险不变量

**问题与证据：**

- §4.3、§7.3、§10.2、§17 和 §18 均规定：已发出但无响应头的请求，在孤儿扫描完整覆盖 3 轮且超过 120min 后，若仍无日志匹配就转为 `failed_unbilled` 并释放槽位。
- 需求决策 15 的硬约束是“槽位只能在 `settled` 或**确认无消费**的 `failed_unbilled` 后释放”；日志缺失、延迟超过窗口、扫描接口漏数或 New API 在写日志前故障，都只是“仍未知”，不是“确认未消费”。
- 当前设计对有 request ID 但回填穷尽的请求会转 `unbilled` 并继续占用；反而对证据更弱、连 request ID 都没有的请求在超时后释放，风险语义倒置。
- §7.2 在准入时就写 `remote_attempt_at`，无法区分“准入后、真正发出前崩溃”与“已经发出后崩溃”，因此也不能据该字段证明未发送。

**影响：** 上游已经产生消费但日志迟到或缺失时，槽位会被错误释放；用户可继续发起新请求，风险占用上限不再是硬上限。迟到日志随后出现时，还会遇到已经标记“不计费”的本地行，形成补扣、冲正和审计歧义。

**必须修改：**

1. `failed_unbilled` 只接受正向证据：连接明确未建立、持久化的 dispatch marker 证明尚未进入发送阶段，或远端日志明确给出失败且 `quota=0`；“在窗口内没找到日志”不能作为入口。
2. 无 ID 的 `open` 超过收敛窗口后应转 `unbilled`（或专门的 unresolved 状态）并继续占用/冻结，等待人工闭环；迟到日志仍可把它结算，不得丢失关联入口。
3. 把“准入时间”和“开始发送”拆成两个耐久字段：准入先落行，紧接着在 fetch 前持久化 `dispatch_started_at`。字段为空可证明没有执行发送步骤；字段非空但无结果一律按未知处理。
4. 增加“日志迟到超过 120min”“日志永久缺失”“准入后、dispatch marker 前崩溃”“dispatch marker 后、socket 写出前崩溃”测试，断言只有可证明未发送的路径释放槽位。

#### R2-P0-2：运行 Key 租约只 fencing 本地写回，不能 fencing 远端副作用

**问题与证据：**

- §8.2 的 `creating` 租约固定 30s，但赢家在租约内要先执行 `ensurePortalUserBinding()`，再执行 `client.createKey()` 的“查找 → 创建 → 再查找 → 取明文”多次网络调用。现有 `client.ts` 单次调用超时为 15s，GET 还可重试一次，整个序列合法地超过 30s。
- A 持有者仍在远端调用时租约到期，B 可接管同一代次。A/B 都可能先查不到同名 token 后各自 POST；需求 16.2 已实测 New API **允许同名 token 重复创建**。最终 `lease_holder` CAS 只能阻止旧持有者覆盖本地行，不能撤销它已经创建的远端 token，CAS 失败后“直接放弃”会留下启用但不受本地追踪的凭证。
- 现有 `findTokenByName()` 只扫描第一页前 100 条并取第一个同名项（`client.ts:829-834`），既不能确认同名唯一，也不能处理已经存在的多个同名 token；v2 仍声明直接复用该方法。
- `retiring_token_id` 只有一个槽位。第一次轮换完成后行已恢复 `active`、旧 token 尚在宽限期，第二次轮换仍满足 `WHERE status='active'`，会覆盖第一个 `retiring_token_id`；`invalid → creating` 分支也没有把当前坏 token 明确搬入退休队列。旧凭证可能永久保持启用。

**影响：** 并发接管、慢请求、连续轮换或 invalid 叠加时可能产生远端活跃凭证泄漏；本地显示只有一个 active Key，但 New API 实际存在多个可调用 token，凭证撤销和事故处置均不可信。

**必须修改：**

1. 给创建流程增加 lease epoch/fencing token 和持续续租；每个远端写副作用前重新确认所有权，CAS 写回失败时对本次确切创建的 token 执行补偿禁用并记录审计。
2. 扩展客户端为“按名称拉取全部匹配项（完整分页/服务端搜索）”，明确 0、1、多个匹配的处理；多个匹配不能任取第一条，必须收敛为唯一启用项或 fail-closed 交人工处理。
3. 退休凭证改为独立追加式 retirement 表/队列，或在数据约束上禁止已有 retiring token 时再次轮换并为 invalid 场景提供不覆盖旧槽位的路径；仅一个 `retiring_token_id` 无法表达多次连续换代。
4. 为 `generation` 增加命名长度约束或使用固定宽度/base36 编码；当前“gen ≤ 999”没有数据库或服务层约束，不能作为 30 字符上限证明。
5. 增加“远端调用阻塞超过租期 + 旧持有者恢复”“预存两个同名 token”“上一代尚未退休时再次轮换”“轮换宽限期内当前代 invalid”测试，断言远端最终只有预期凭证处于启用状态。

#### R2-P0-3：`orphan_remote` 的“照常扣费”没有可执行的原子事务

**问题与证据：** §10.2 要求无法唯一匹配的远端日志创建 `orphan_remote` 行，并“扣费照常结算”、继续占用风险槽位等待人工核查。但 §6.2 唯一结算事务的第一步只允许：

```sql
UPDATE request_ledger
   SET status='settled', ...
 WHERE id=:ledgerId AND status IN ('open','pending_backfill');
```

因此新建的 `orphan_remote` 不能进入该事务。若先改成 `settled` 才扣费，会丢失 unresolved orphan 状态并立即释放风险占用；若保持 `orphan_remote`，当前设计又没有定义“保持状态不变 + 写 charged 字段 + 插入 request_charge + 更新余额/冻结”的独立事务。§7.3 的人工闭环也只写 `resolved_at`，没有说明 orphan 在此之前是否已经扣费、闭环时如何防止再次扣费。

**影响：** 实现者只能在“孤儿不扣费”“扣费但丢失人工核查/风险占用”“另写一个未设计的资金事务”之间自行选择，直接破坏需求对 orphan“归用户、usage 与扣费精确，且未决时保持风险占用”的保证。

**必须修改：**

- 明确定义 orphan 原子入账事务：以 `newapi_request_id` 唯一插入/认领 orphan，在同一事务内写 usage/金额、插入唯一 `request_charge`、更新 `wallet_account` 和透支冻结，同时保持 `status='orphan_remote'`、`resolved_at=NULL`。
- 或把“计费状态”和“归因/人工核查状态”拆成正交字段，避免一个 `status` 同时承担两种状态机；无论选哪种，都必须给出数据库 CHECK、唯一索引和合法迁移表。
- 人工 resolve 只能补归因、说明或产生显式冲正/调整，不得隐式重复扣款。
- 增加同一孤儿日志被两个 batch worker 并发发现、已扣费 orphan 再次同步、人工补归因、人工冲正四类事务测试。

#### R2-P0-4：备份门禁与阶段 ① 的真实钱包写入顺序互相矛盾

Claude 对需求原文“实现前必须完成边界**定义**”的口径校准是成立的；问题在于 v2 自己的激活顺序仍未闭环：

- 冻结需求 §13.1 的阶段 ① 只包含“钱包账本**结构**”，明确“不影响线上真实调用”。
- v2 §13.1 却把“充值 PAID 事务写 `wallet_ledger`、停止写充值 credit、余额展示切 `wallet_account`”放入阶段 ①；这已经让真实支付数据进入新事实链，不只是建表和管理面。
- 恢复实现与真实演练门禁被放在阶段 ② 切流前，且正文又声明“未过门禁不得开始钱包迁移”。阶段 ① 的钱包双写已经先于这句话开始迁移；`WALLET_DISPLAY_ENABLED` 只控制展示，不能阻止 ledger 写入。

**影响：** 若阶段 ① 与阶段 ② 分窗发布，恢复演练尚未完成时系统就会产生不可丢失的新钱包流水；此时“切流前有门禁”不能保护已经写入的资金数据。

**必须修改：** 二选一并写成机器可执行门禁：

1. 将恢复实现 + 演练门禁前移到任何真实 `wallet_ledger` 写入和余额来源切换之前；或
2. 阶段 ① 只部署 schema/代码且默认 dormant，增加独立 `WALLET_LEDGER_WRITE_ENABLED=false` 硬开关，演练通过并记录 gate evidence 后才在同一受控步骤启用双写与展示。

测试与 runbook 必须证明：门禁未满足时支付成功仍走原事实链且不会写新钱包；门禁满足后首笔双写原子、可备份并能从演练快照恢复。

### 21.3 重要缺口（P1）

#### R2-P1-1：cache “逐维硬校验”仍缺少可审计数据模型，并允许以对账容差放宽硬方向

**问题与证据：**

- `model_price_version` 只快照 `newapi_ref_input` / `newapi_ref_output`，没有三维 cache 参照价、证据 ID、观测时间、来源指纹或失效状态；§5.3 说“同款证据结构存档”，但 §3 没有对应表或字段。发布后 catalog 同步值变化时，历史价格版本无法复原当时用什么 cache 证据通过门禁。
- S5-乙声称“一次真实 cached 调用”可由总 `quota` 反解“各 cache 维度单价”。若一次调用同时出现普通输入、输出、cache read、5m write、1h write，而日志不直接给出每维 ratio，这是一条总金额方程对应多个未知数，数学上不可唯一求解。现有客户端已经能解析日志 `other` 中可能存在的 `cache_ratio` / `cache_creation_ratio_*`，应优先验证并持久化这些显式字段；只有 aggregate quota 时需要设计多组隔离变量的受控实验，不能宣称一次调用恒可行。
- §5.3 对 input/output 又允许“在 §10.4 容差内相等”。`max(10 micro-USD, 1%)` 是运行期金额对账容差，不是发布方向容差；允许低 1% 仍会使“门户单价 ≥ New API 实际单价”的硬约束失真。

**要求：**

1. 增加不可变的 cache reference/evidence 数据模型，价格版本快照三维参照价及 evidence ID/fingerprint/observed_at；倍率或证据源变化时旧证据失效并阻止新发布。
2. 发布方向使用整数交叉相乘或等价精确比较；参照价有分数时向成本侧保守取整，不使用金额对账容差放宽 `portal >= newapi`。
3. 把 S5-乙拆成可验证分支：日志显式 ratio 法，或多次受控调用的独立方程法；无法唯一求解即保持 fail-closed。
4. 增加“仅低 1 micro-USD/M 也拒绝”“catalog 参照更新后历史版本仍可复核”“证据指纹变化立即失效”“aggregate quota 方程不可解时拒绝发布”测试。

#### R2-P1-2：非流式响应 `arrayBuffer()` 没有任何上限，不满足同进程网关的内存边界

§4.4 把非流式响应描述为“响应体天然有界”，随后直接 `await upstream.arrayBuffer()`；但设计没有响应大小上限，也不能信任 `Content-Length` 一定存在或真实。一个超大/分块上游响应会把完整 body 一次性驻留在门户进程内，可能同时拖垮网关与 UI。请求体 25MB 上限和模型 token 配置都不能证明响应字节上界。

**要求：** 非流式也走背压透传，并只为 usage 解析维护有界旁路缓冲；超过解析上限时停止累计、用户 body 继续透明下发，账本转日志回填。增加无 `Content-Length` 的超大 chunked 响应、并发大响应和旁路缓冲超限测试，断言内存上界与响应总长度无关。

#### R2-P1-3：后台 job 锁允许同实例重入，长任务还缺少跨实例 fencing

§10.1 使用 `setInterval(tick)`，并允许 `WHERE lease_until < now OR holder=self` 抢锁。异步 tick 超过周期时，`setInterval` 会再次触发；同一实例因 `holder=self` 可直接再次进入。`backfill` 周期仅 5s，而现有 New API 单次请求超时 15s，重入不是边缘情况。两个 tick 可能重复查询同一行、并发增加 attempts、提前耗尽回填次数或重复触发外部调用。

同时，租期固定为 2 × 周期且任务执行中没有 heartbeat/epoch；任务超过租期后另一实例可接管，旧实例仍继续执行。仅声明“所有 job 幂等”不能替代领取协议，尤其是孤儿入账、渠道 smoke、凭证退休等包含外部副作用的任务。

**要求：**

- 调度改为 await 本轮完成后再安排下一轮，或至少增加进程内 running guard；同 holder 不得绕过正在执行检查。
- DB 租约增加 epoch/fencing token 和执行中 heartbeat；写入结果必须校验 epoch。
- 对 `pending_backfill` 等工作行增加条件 claim/lease，使一个批次只有一个 worker 获得远端调用权。
- 增加“tick 时长大于周期”“执行中租约过期并由第二实例接管”“旧 worker 恢复提交结果”测试，验证 attempts、孤儿扣费和外部调用均不会重复。

### 23.2 阻塞项（P0）

#### R3-P0-1：运行 Key 的“远端 fencing + 补偿”仍不可执行，并存在把当前 token 禁用的竞态

**问题与证据：**

1. §8.2 步骤 c 假定 `POST /api/token/` 后可“记录返回 token id”。但需求固定的 New API commit 中，`AddToken` 成功响应只有 `success` 与 `message`，**不返回新 token ID**；现有 `client.ts:1248-1265` 也正是忽略 POST 响应、随后按名称重新查询。该固定版本源码见 [`controller/token.go::AddToken`](https://github.com/QuantumNous/new-api/blob/6ce7305cd36f16506fb6a2c3c524a5a318539ba7/controller/token.go#L190-L233)。
2. 需求 16.2 已实测同名 token 可重复创建。若两个执行者都跨过“查无同名项 → POST”窗口，事后完整分页只能得到两个同名 ID，无法证明哪一个由哪个执行者创建，因此 §8.2 e 所需的“本执行者持有其 id”并不成立。
3. `SELECT lease_epoch == myEpoch` 与远端 POST 不是一个原子操作。执行者 A 可在 SELECT 后暂停，租约到期后 B 接管并 POST，A 恢复后仍会 POST；客户端 epoch 最多 fence 本地 CAS，无法让不识别 epoch 的远端拒绝旧执行者。§15.2 要求该场景“无双 POST”是当前协议下不可满足的测试预期。
4. 即使 A 确实拿到了自己创建的 `tokenId`，当前补偿仍会误伤赢家：A POST 出 T 后暂停；B 接管、按同名唯一结果收编 T 并把本地行置 active；A 恢复后 active CAS 失败，按 §8.2 e 把 T 立即加入退休队列；retire job 随后会禁用 **B 当前正在使用的 T**。现有退休任务没有“该 token 已成为当前 active token 时取消退休”的状态或原子守卫。

**影响：** 慢调用、事件循环停顿或进程恢复时，系统可能留下无法归属的重复远端凭证，也可能把接管成功后的唯一当前凭证禁用。§8.2 的“最终恰有一个启用 token”收敛证明不成立，凭证泄漏与数据面 401/503 都可能发生。

**要求：** 复审前必须选定一个在现有远端契约下可证明的方案，而不是继续把本地 epoch 称为远端 fencing：

- 若坚持自动收敛，需增加**耐久的创建 attempt 身份**，让每次可能 POST 的尝试在远端具有可唯一识别的名字/幂等键，并定义“候选 token → 当前 token”的原子选择；退休只处理已证明未被选中的 token。
- 若要依赖“POST 返回 ID + 幂等创建”，则必须把 New API 修改明确纳入范围，给出接口/唯一约束/部署顺序；仅修改门户 client 不足以获得该能力。
- `credential_retirement` 必须有 claim 状态与“不得禁用当前 active token”的竞态闭环；接管收编和补偿入队之间要有同一份可验证的 token 归属事实源。
- 测试至少覆盖：所有权复核后暂停再接管、POST 成功但响应不含 ID、赢家收编败者创建的单个 token、多个同名 token、败者补偿与赢家 active CAS 交错、进程在 POST 后再次崩溃。断言应区分“严格不重复创建”和“允许短暂重复但可自动安全收敛”，不得同时承诺两种互斥语义。

#### R3-P0-2：`orphan_remote` 缺少可唯一确定门户价格版本的信息，当前“创建即扣费”可能扣错金额

**问题与证据：**

- §6.2 把孤儿金额定义为“远端日志时间点该 `(分组, 模型)` 的 active 价格版本”。但 `model_price_version` 的键是 `(portal_group_id, portal_model_id)`；远端日志只有 `newapi_group`、模型和运行 Key，`orphan_remote` 又按需求明确允许 `portal_group_id`、路由版本与价格版本为空。
- 多个门户分组完全可以把同一模型路由到同一个 New API 分组，同时配置不同门户价格。运行 Key 又按 `(portal_user_id, newapi_group)` 共享，因此从 token 名、New API 分组和模型无法反推出唯一门户分组。连接 `model_route` 历史表也只会得到多个候选版本，不会得到唯一答案。
- 即使候选门户分组唯一，用“远端日志时间”选择价格也不等于请求准入时锁定的版本；请求跨过调价时点时，日志完成时间可能命中新版，而真实请求应使用旧版。
- §6.2 所说“极端无版本命中理论不可能”也不成立：观察期旧 token、人工直连、路由退休后的迟到日志或历史数据都可能产生无当前候选的日志。

**影响：** 唯一索引和单事务只能保证“一次扣款”，不能保证“扣对金额”。当前方案可能任取某个门户分组的价格、按错误调价时点计费，破坏需求 7.8/14.5 对孤儿 usage 与扣费可追溯的承诺。

**要求：** 在需求层先裁决“无法恢复锁定价格版本时如何计费”，然后让数据模型可执行。可选方向包括：

1. 调整运行凭证/远端可观察标识的粒度，使一个日志可唯一映射到门户计价 cohort；这会改变当前“用户 + New API 分组共享一把运行 Key”的边界，需要同步修需求。
2. 只有在候选账本行推导出**唯一且相同的价格版本/金额**时自动扣费；多候选不同价或零候选时先认领远端请求并保持未决，待人工归因后再走原子扣费。若这与“孤儿创建即扣费”冲突，应由需求明确取舍。
3. 若业务接受保守价/最高价/最低价等确定性替代，必须在需求中承认其不是精确锁定价，定义用户权益、冲正与审计规则，不能在设计中称为“最接近即可精确扣费”。

新增验收必须至少包含：两个门户分组同模型同 New API 分组但价格不同；同一用户多个无 ID open 候选；请求跨价格发布时间；无任何候选价格版本。以上场景均不得静默任选版本扣款。

#### R3-P0-3：钱包激活、Caddy 切流和“一键回滚”之间存在明确的绕钱包计费窗口

**问题与证据：**

- §13.1 要求先在 ①.5 打开 `WALLET_LEDGER_WRITE_ENABLED`/展示开关并完成首笔真实充值验证，之后才在 ② 把 Caddy `/v1` 从 New API 切到门户。在两步之间，充值已经进入门户钱包且停止写 credit，但外部推理仍可能携旧 Key 直达 New API；这些请求只扣 New API quota，不写 `request_ledger` 和 `wallet_ledger`。
- §13.2 的 72h 回滚更直接：只把 Caddy 上游改回 3001，旧 token 又恢复可用，但钱包开关、余额展示和充值路径仍留在新语义。回滚期间的全部推理消费都会绕过门户钱包；再次切回网关后，门户余额将高于实际可支撑余额。
- 需求 13.1 明确 ① 与 ② 是“同一个不可拆分的上线门禁”。“同一发布窗口”不是互斥/停流原语，不能证明窗口内没有请求；当前 runbook 也没有维护模式、冻结充值、流量排空、起止水位或回滚补差步骤。

**影响：** 正常切流或故障回滚都可能造成可实际消费但门户未扣费的资金缺口；“Caddy 改回即可安全回滚”这一承诺不成立。

**要求：**

- 把 ①.5 与 ② 重写为**有流量静默边界的原子运维过程**：先阻断外部充值与 `/v1` 新请求/等待在途排空，记录 New API 日志与余额水位，再激活钱包并切 Caddy、封旧直连入口，验证后再开放流量。若利用“当前无真实用户”简化，也要把“只允许受控 smoke 身份且其他入口物理阻断”写成可验收门禁。
- 回滚不得只写 Caddy 操作。要么保留一个仍经过门户鉴权和账本的降级数据面；要么进入显式 legacy/maintenance 模式，冻结充值和新调用，并定义回滚期间 New API 消费如何导入/冲正门户钱包后才能再次前滚。
- 增加“钱包开关已开但 Caddy 未切”“网关运行 10 分钟后回滚直连并产生消费”“回滚后再次前滚”测试/演练，核对两侧余额、请求账本和充值事实源无缺口。

### 23.3 重要缺口（P1）

#### R3-P1-1：后台 job 的 epoch 没有贯穿工作行与结果提交，旧 worker 仍可在接管后写回

§10.1 的 `backfill_claimed_until` 只有过期时间，没有 `claim_holder` 或 `claim_epoch`；§3.6 也只增加了这一个字段。A 已成功 claim 并发起远端调用后，claim 到期，B 可以再次 claim；A 恢复时不会重新执行 claim，因此正文所说“被接管后旧 worker 的 claim 失败”与实际时序无关。设计没有要求 attempts、回填结果或状态迁移以 `claim_epoch=:mine` 为条件，§15.2 声称“旧 worker 写回被 epoch 拒绝”目前没有可落到 SQL 的字段。

此外，§10.1 沿用“租期 = 2 × 周期”，backfill 周期为 5s，因此租期恰好 10s；心跳也是每 10s，零安全余量，任何调度抖动都可能先过期再心跳。§3.9 的 `gateway_job_lock` 字段仍没有正文所依赖的 `epoch`。

**要求：** job 锁租期必须与调度周期解耦，并满足明确的心跳安全余量；工作行增加 holder + 单调 epoch（或等价 claim token），领取、attempt 递增、结果写回和 claim 释放全部带 token 条件。失去全局租约时传播取消信号；无法取消的远端调用返回后也只能提交到仍持有相同 claim epoch 的行。渠道 smoke、凭证退休等有外部副作用的 job 要逐项声明 at-most-once、at-least-once 或幂等依据，不能用一个泛化的“upsert/条件 UPDATE 幂等”覆盖远端调用。补充 A 阻塞过期、B 接管完成、A 恢复写回的确定性测试。

#### R3-P1-2：cache 证据表既无法追加新版本，也无法用一个 FK 引用三维证据

§5.3 定义 `price_reference_evidence` 在 `(newapi_group, newapi_model_id, dimension)` 上普通唯一。证据失效后若 INSERT 新观测会撞唯一约束；若 UPDATE 原行又会覆盖旧证据，使历史 `model_price_version` 无法复原“当时凭什么通过门禁”。这与“可失效、可历史复核”目标直接矛盾。

同时，cache 三个 dimension 是三行证据，`model_price_version` 却只增加一个 `cache_evidence_id`，无法表达三维分别来自不同 evidence 行/方法。§3.3 的正式字段表甚至仍只列 input/output 两个 New API 参照价，没有第 5.3 节声称已经加入的三维快照列和 evidence 引用。

`log_ratio`/`controlled_probe` 的失效也不能只依赖“模型倍率 + 分组倍率”指纹：cache 专用 ratio 可独立变化而基础倍率不变，当前没有 TTL、定期重测或 cache ratio 指纹来发现这种变化。

**要求：** 采用追加式 evidence 版本（例如 observation/evidence set 父表 + 三维明细），只对当前 valid 版本做部分唯一；价格版本引用一个完整 evidence set，或分别引用三个 evidence ID，且引用对象永不覆盖。失效应同时覆盖基础倍率变化、cache ratio 变化与证据超龄。测试 stale→重测→新发布后，旧/新两个价格版本必须各自可还原三维原始证据。

#### R3-P1-3：32MB 是单请求上限，不是门户进程的总内存上界

§4.4 给每个非流式请求分配最高 32MB 的旁路解析缓冲，只证明内存不随**单个响应长度**继续增长；风险槽位是每用户上限，并没有全局并发上限。100 个不同用户并发即可仅解析缓冲占约 3.2GB，还未计入 25MB 入站 body、流队列、Next.js UI 与其他进程内状态。因此 §15.2 的“并发大响应不 OOM”没有参数化的、可证明的系统边界。

**要求：** 增加进程级总解析预算/加权信号量（预算不足的请求立即放弃旁路解析、继续透明透传并转日志回填），或给出等价的全局并发与内存预算证明；明确单请求上限、全局预算、容器 memory limit 和降级顺序。测试应以 `并发数 × 单请求上限 > 全局预算` 构造压力，断言实际旁路占用不超过全局预算且用户响应不被截断。

### 25.2 阻塞项（P0）

#### R4-P0-1：主动轮换与 janitor/retire 协议仍会把新代 token 收编回旧代或在激活竞态中禁用

**问题与证据：**

1. §8.2 声明“所有取得执行权的路径”都执行 `lease_epoch+1`、把当前 `remote_name` 保存为 `prev_remote_name`，然后步骤 c 优先收编 prev。若主动轮换遵守该总规则，prev 就是待退休的旧 active token，步骤 c 会把它重新收编为新代，根本不会创建“新名新 token”；10 分钟后退休任务发现它又是当前 token，只能取消退休，轮换语义失效。
2. 若把 §8.4 的 CAS 当作独立例外逐字执行，它又只写 `remote_name=f(gen+1)`，既缺 epoch 参数，也没有明确递增 `lease_epoch`、清空 `prev_remote_name` 或建立新的 attempt 所有权。两种解读都无法得到唯一且可实现的状态机。
3. §8.1/§8.2 把“scope 前缀下 id 不等于当前 `newapi_token_id`”定义为任意时刻都可退休。行处于 `creating` 时，新 POST 的 token 尚未 CAS 写成 current，周期 janitor 可先把它入队；retire worker 的禁用前复核也可能发生在 active CAS 之前，随后远端禁用、创建者再把已禁用 token 写成 active。一次 DB 查询与后续远端 PUT 之间不是原子区间，因此“禁用前再查一次”不能结构性消除该 TOCTOU。
4. `credential_retirement` 只定义 `disabled_at`，却要求“等于当前 token 时取消退休项”，同时又宣称队列 append-only 且 `newapi_token_id` 唯一。删除会丢审计，保留空 `disabled_at` 会反复领取，伪造 `disabled_at` 又会谎报已禁用；以后该 token 真正需要退休时，唯一约束还会阻止重新入队。

**影响：** 应急轮换可能继续使用已泄漏旧 Key；正常创建/接管也可能把刚创建的新 Key 禁用后登记为 active。两者都会造成安全边界失效或数据面持续 401/403，属于实施阻塞。

**必须修改：**

- 把“接管旧 attempt”和“运营轮换新 generation”拆成不同转移：只有接管/同代失败重试允许收编明确的前一 attempt；轮换/invalid 必须清空可收编指针并创建新 generation、新 epoch、新名字。
- 给远端 attempt 建立可持久化的在途保护，或给出等价协议：janitor 只能处理稳定 `active` 范围，不能把当前 creating attempt、可收编 attempt 或已获执行权但尚未落 active 的 token 判为 stale；一旦退休项进入可禁用状态，任何 active CAS/收编必须再也不能选择该 token。
- 为退休项定义明确状态机，例如 `pending / claimed / cancelled / disabled`，记录取消原因和时间，并说明取消后未来如何重新退休；不能用“查询后远端 PUT”冒充原子守卫。
- 增加确定性竞态测试：轮换时 prev 指向旧 active、janitor 夹在 POST 与 active CAS 之间、retire 复核后 active CAS、取消后再次真实轮换。断言最终 active token 是启用的新代，旧代可审计且只被禁用一次。

#### R4-P0-2：孤儿两段式仍可能按事后可变状态错扣，并允许未扣费记录直接 resolve 释放

**问题与证据：**

1. §6.2 的自动候选集使用“该用户可访问”的门户分组，这是查询时的可变现状，不是请求发生时的耐久事实。示例：请求时 G1/G2 都可能映射到同一 New API 分组，实际来自 G2；日志入库前 G2 权限被撤销，候选集只剩 G1，系统会把“候选唯一”误当成事实并按 G1 自动扣费。
2. §10.2 在多个本地 `open/unbilled` 候选时另建 orphan，但没有保存 orphan 与这些候选行的关系，也没有规定候选行随后如何结算、核销或继续占槽。同一远端消费会形成“一条 orphan + 多条原未决行”的悬挂集合，人工界面没有可执行的一对一裁决入口。
3. §6.2 把“扣费”和“归因闭环”定义为两个动作；§7.3 又允许对任意 orphan 直接写 `resolved_at` 且“不隐式动钱”。因此未扣费 orphan 可以先 resolve 并释放风险槽位，此后既不再占用，也没有约束保证产生 `request_charge`。这与需求 §7.8、§14.5 明确要求 orphan 可追溯 usage **与扣费**、消费金额不丢失相冲突。
4. 多候选同价时正文要求“记全部候选供审计”，但 `request_ledger` 只有一个 `price_version_id`，没有候选快照表或 JSON 字段，无法还原当时比较了哪些锁定版本。

**影响：** 当前设计同时存在静默错扣、消费漏扣和风险槽位被提前释放三条资金错误路径，不能交给实现阶段自行猜测。

**必须修改：**

- 自动扣费只能基于不可变候选证据。最保守且可执行的一期规则是：仅从实际命中的多个未决账本行读取其已锁定 `price_version_id`；零候选或缺少请求时点访问快照时一律留人工。若坚持从历史路由反推，必须新增用户分组可访问历史并按请求时间重建完整候选集，不能读取当前权限。
- 新增 orphan-candidate 关系或等价耐久快照，记录候选账本行、门户分组、路由/价格版本及排除理由；明确人工选择后，被选行、未选行和 orphan 各自的状态迁移及风险占用语义。
- 人工闭环必须是单一原子动作：未扣费 orphan 先确定价格并写 `request_charge`/余额，再写 `resolved_at`；若业务允许免收或核销，必须有显式 `waived/writeoff` 结果与审计流水。增加数据库可表达的不变量：`resolved orphan => 已扣费或有显式免收结果`。
- 增加权限在请求后变更、多个候选同价、零候选、未扣费直接 resolve、人工选择一个候选后的全集合收敛测试。

#### R4-P0-3：静默窗只封 api2，钱包激活前后仍存在公开 New API 直连后门

**问题与证据：**

1. §1.3 已确认 `newapi.apipool.dev/v1*` 当前公开直连 New API。§13.2 步骤 2 只让 api2 `/v1*` 返回 503，直到步骤 5 才给 newapi 域名增加 `/v1*` 屏蔽；步骤 4 已先打开钱包、恢复充值。于是步骤 2–5 期间旧 token 仍可经 newapi 域名消费，只扣 New API quota，不进入门户账本，恰好重现本轮要消除的 ①.5→② 绕账窗口。
2. “New API 日志静默 ≥2min”不能证明在途排空。设计允许流式请求总时长 3600 秒；一个更早开始、仍在输出的长流可以在最近两分钟没有新日志，却仍在水位记录后继续产生消费。
3. 三个钱包/充值开关都按 env 描述，但 runbook 没说明它们是运行时配置、进程重启生效还是发布重建生效，也没有给出多实例一致切换和失败回退顺序。“原子运维过程”因此仍不是机器可执行协议。

**影响：** 钱包启用水位可能从诞生时就少记消费；步骤 6 的水位核验只能事后发现，不能防止错误余额已经对用户可见或充值已经进入新语义。

**必须修改：**

- 进入静默窗的第一步同时封堵 `api2.apipool.dev/v1*` 与 `newapi.apipool.dev/v1*`，并以两个外部探测成功作为记录水位、激活钱包的硬前置；步骤 5 只能开放 api2 到门户，newapi 屏蔽持续保持。
- 用可观测的 active connection/request 计数证明排空，或在停止新流量后等待/强制终止到设计最大时长；不能仅以日志静默替代 drain。水位必须记录在确认排空之后。
- 固化开关的配置事实源和生效方式，写出重启/reload、多实例一致性、失败回退以及每一步的可重复探测。回滚补差还应为每个回滚窗口定义稳定幂等键，避免重复导入。

### 25.3 重要缺口（P1）

#### R4-P1-1：响应解析预算已封顶，但入站 body 在准入前仍可把同进程内存打满

§2.4 步骤 3 在粗余额门禁、运行 Key 和原子准入之前读取整个请求体；§4.3 允许每请求 25MB，并对整段 JSON.parse。`GATEWAY_PARSE_BUDGET_TOTAL` 只约束响应旁路缓冲，§4.4 所写“解析预算 + Σ(25MB × 并发) + …”中的并发没有全局上限，因此只是容量估算式，不是进程内存上界。单个已认证 Key 可并发发送大量 chunked body，在任何风险槽位被占用前造成 OOM；字符串解码与 JSON 对象还会进一步放大驻留量。

**要求：** 在读取 body chunk 时就接入进程级请求字节预算/加权信号量，或给出等价的全局并发与流式落盘方案；预算不足应在大额分配前返回 429/503 并释放已占预算。`Content-Length` 只能做快速拒绝，不能替代对 chunked body 的实际字节记账。测试需构造 `并发 × 25MB > 全局 body 预算`，断言进程峰值受限、预算释放无泄漏且未进入原子准入/远端转发。

#### R4-P1-2：设计依赖的维护任务未进入任务清单，TTL 门禁可在任务停摆时失效

§8 依赖低频 janitor 和 retire job 自动收敛，§5.3 依赖证据超龄后置 stale；但 §10.1 的可执行任务表只有 `backfill`、`batch_sync`、`sweeper`、`channel_guard`、`reconcile`、`wallet_invariant`，没有 credential janitor、credential retirement 或 price evidence expiry 的 job 名、周期、租约/领取方式和失败告警。尤其价格发布只依赖 evidence 当前 `status=valid`；若过期任务延迟或停止，超过 30 天的证据仍能通过发布硬门禁。

**要求：** 把上述任务正式加入 §10.1、env、观测和测试清单；价格发布时必须同步校验 `observed_at + TTL > now`，异步任务只负责状态卫生和告警，不能承担硬门禁唯一正确性。增加任务停摆后尝试发布、进程重启补扫、重复领取和退休失败重试测试。

### 27.2 阻塞项（P0）

#### R5-P0-1：换代事务没有把旧 token 移出“当前 token”字段，“退休集合与当前集合不相交”的证明尚未成立

**问题与证据：**

1. §8.2/§8.4 的换代型 CAS 把旧 `newapi_token_id` 插入 `credential_retirement`，却只更新 generation、epoch、remote_name、prev 和 status，**没有清空或迁移 `newapi_token_id/token_enc/key_masked`**。事务提交后，同一个 token 同时存在于活跃退休项和行上的“当前 token ID”字段，直接反例于 §0#6、§8.2 所称的两个集合恒不相交。
2. §3.4 又规定 retire worker 发现队列 token 等于任一行当前 token_id 时执行 `claimed → cancelled`。若新代创建失败、行落 `failed`，10 分钟后旧泄漏 token 仍在该字段中，退休项会被取消，主动轮换最需要作废的旧 token 反而永久保持启用。若“当前”实际只指 `status=active` 的行，正文必须把这个谓词写进断言；当前字段定义、伪代码和证明均未如此限定。
3. retire 状态机虽然增加 `claimed_until/claim_epoch`，但只写了 `pending → claimed → disabled/cancelled`，没有定义 worker 在远端禁用前后崩溃时如何以 `claimed_until < now` 重新领取 claimed 行。按逐字实现，崩溃后的项可能永久卡在 claimed。
4. §8.4 的用户禁用仍直接描述“异步批量禁用 active Key”，没有把 runtime 行原子迁移到 `disabled`、清空当前归属或接入 retirement 状态机；而 §3.4 又保留 `reason=user_disable`。两处无法确定同一套“在队即出局”规则是否适用于用户禁用。

**影响：** 泄漏应急轮换、invalid 换代或用户禁用可能在本地显示已进入退休流程，远端旧 Key 却因防御断言取消或 claim 卡死而继续有效。这是凭证安全边界的实施阻塞。

**必须修改：**

- 固化“当前 token”的数据库谓词。推荐在换代 CAS 中把旧 ID/密文复制入 retirement 后清空 runtime 行的 active token 字段；若保留字段作历史快照，则新增独立字段并把所有防御查询明确限定为 `runtime_credential.status=active`。
- active 落库必须与“token 不在 pending/claimed retirement 中”形成同一 DB 条件；不能只在落库前做一次服务层查询。
- 给 retire job 写出 expired claimed 的重新领取 SQL、claim epoch 条件写回及“远端已禁用、本地未提交后重试”的幂等路径。
- 用户禁用必须明确采用同一事务的 runtime 状态迁移 + retirement 入队，或完整定义一套独立但同样可恢复的队列；不能停留在“异步批量”叙述。
- 增加确定性测试：轮换后新代创建失败且宽限到期、retire 远端成功后进程崩溃、claimed 租约接管、用户禁用与创建并发。断言旧 token 最终禁用且当前/退休集合从未重叠。

#### R5-P0-2：`superseded` 裁决按现有唯一约束不可执行，waived 仍会丢失消费金额

**问题与证据：**

1. 段一创建 orphan 时，真实 `newapi_request_id=R` 已由 orphan 行占有，且 §3.6 定义全表唯一索引。§6.2 的 superseded 事务随后要求把同一个 R 回填到候选行 X 并结算 X；这会立即命中唯一约束。
2. 试图先把 orphan 的 request ID 清空也不可行：§3.6 的 CHECK 要求 `status=orphan_remote` 时 request ID 非空；状态枚举又没有 `superseded`，也没有 `superseded_by_ledger_id` 字段。`resolve_outcome=superseded` 只是一段文字标签，既不能转移唯一所有权，也不能记录最终选择了哪个候选行。
3. `waived` 仅要求原因、审计和告警，没有锁定 `price_version_id`、理论应收金额或任何 offset/write-off 流水。需求 §7.8/§14.5 要求 orphan 可追溯 usage 与扣费、消费金额不丢失；当前 waived 可以把一笔消费以未知金额直接释放。
4. 多候选时所有原 `open/unbilled` 行继续占风险槽位，段一又新增一个未决 orphan 槽位。用户原本恰有 10 个占用时，批量同步可把计数推到 11，违反 §0#4 和需求 §8.4 的“任何时刻未决消费数不得超过上限”；同一远端消费也被候选集合与 orphan 重复占用。

**影响：** 人工选择“归属候选行”会事务失败；选择 waived 会使金额证据消失；批量恢复还可能破坏风险上限不变量。孤儿资金闭环仍不可实现。

**必须修改：**

- 先选定唯一的 request-id 所有者，再设计迁移。可选方案包括：保留 orphan 为权威行，使用 X 的锁定版本补齐 orphan 的门户归因并把 X 标为被 orphan 吸收；或新增真正的 superseded 状态/外键与审计字段，在同一事务内把唯一 ID 转移给 X。无论选择哪种，唯一索引、CHECK、状态枚举、结算守卫和查询路径必须同时给出。
- 增加 `superseded_by_ledger_id` 或等价强类型关系，不能只依赖 JSON 候选快照和 resolve_note 表示最终裁决。
- 若保留 waived，必须先锁定价格并记录 `waived_micro_usd`/价格版本，最好用幂等 write-off 或“扣费 + 冲正”流水表达净额；否则移除 waived 并先取得需求变更批准。
- 定义 orphan-candidate 集合的风险计数语义，使一笔远端消费最多占一个逻辑风险槽；零候选导致无法证明原子准入时应冻结/告警并显式记录不变量破坏。
- 用真实 libSQL 迁移执行 superseded 事务测试，不能只 mock 服务层；补充满 10 槽时产生 orphan、waived 金额对账和同一 request ID 并发裁决测试。

#### R5-P0-3：`.env.deploy` 并不是当前 Caddy/容器开关的实际事实源，按 runbook 执行不会完成切流

**现有代码复核：**

1. `deploy/configure-caddy.sh:46` 的 `API_UPSTREAM` 只读取**当前 shell 环境**中的 `APIPOOL_API_UPSTREAM`，缺失时直接回退 3001；只有 New API 保护变量在 52–57 行调用 `read_env_value()` 从 `.env.deploy` 读取。
2. `deploy/deploy.sh:48` 调用该脚本时只传 `APIPOOL_DEPLOY_ENV_FILE`，没有导出 `APIPOOL_API_UPSTREAM`。因此 §13.2 步骤 5 仅把 `APIPOOL_API_UPSTREAM=127.0.0.1:3000` 写进 `.env.deploy`，再运行现有配置脚本，生成结果仍会指向 3001。
3. `docker-compose.prod.yml:7-22` 是运行时环境 allowlist，当前没有 `WALLET_LEDGER_WRITE_ENABLED`、`WALLET_DISPLAY_ENABLED`、`APIPOOL_CHECKOUT_ENABLED` 或任何新增 `GATEWAY_*` 变量。只改 `.env.deploy` 并 `compose up -d` 不会把这些值注入门户容器。§14 的文件计划也没有列出 production/local compose 文件。
4. 步骤 2 要让 api2 进入 maintenance、newapi 永久 block，但环境变量清单没有能表达 Caddy 三态的配置，`configure-caddy.sh` 文件计划也只写“newapi 404、api2 注释更新”。当前所谓统一事实源无法表达 `legacy → maintenance → portal`。

**影响：** 最危险的结果是步骤 5 移除 api2 维护响应后，Caddy 仍反代 3001，形成“钱包已激活但请求继续绕过门户”的生产窗口；更保守的结果是钱包开关根本没有进入容器，切换流程永久卡在探针失败。两者都证明 runbook 尚不可执行。

**必须修改：**

- 为 Caddy 定义一个单一、可验证的状态，例如 `APIPOOL_API_MODE=legacy|maintenance|portal`；`configure-caddy.sh` 必须像保护变量一样按字面量读取 `.env.deploy`，并由该状态同时生成 api2 路由与 newapi `/v1*` 屏蔽。也可改为显式 CLI 参数，但不能同时声称文件是唯一事实源。
- 把所有新增服务器运行时变量加入 `docker-compose.prod.yml` 与本地 compose allowlist，并将这两个文件加入 §14 改动清单；以 `docker compose ... config` 验证最终容器环境。
- 建议新增单一 cutover 脚本，复用 deploy lock，按“写配置 → 生成/校验 Caddy → 重建容器 → 探针 → 提交下一状态”推进，并为每一步保存可逆状态；不要让 runbook 依赖人工拼接多个非原子命令。
- 增加 `configure-caddy.sh --print-config` 的三态 fixture、compose config env 注入测试，以及在每个状态转换点注入失败后的回滚测试。portal 模式必须断言 api2 upstream=3000 且 newapi `/v1*`=404。

### 27.3 重要缺口（P1）

#### R5-P1-1：body 预算统计的是网络字节，不是 Node 进程实际持有内存

§4.3 的 chunk 级预算能限制同时接收的原始字节总量，这是有效进展；但实现仍要求形成 `rawBodyText` 并对完整正文执行 JSON.parse。典型路径会同时或先后持有 chunk/Buffer、UTF-16 字符串及对象树，数组/大量短字段的对象开销还能远高于输入字节。`GATEWAY_BODY_BUDGET_TOTAL=256MB` 因此不等于“进程最多多占 256MB”。§4.4 也仍保留旧公式 `Σ(25MB × 并发)`，与新预算叙述冲突。

**要求：** 明确预算的 charge 单位和最坏放大系数，或避免完整对象树：保留一次原始 Buffer、用受限解析器只提取顶层 model，随后按确定时点释放中间对象；容器 memory limit 需包含 V8 heap、external Buffer 和响应预算的安全余量。压力测试除并发 25MB 外，还要加入大量短字段/深层数组的恶意 JSON，按 RSS 与 heap/external 三项断言峰值，而不是只断言记账器数值。

### 27.4 文档一致性问题（P2）

**要求：** 逻辑问题修复后再次从 TL;DR、字段定义、状态机证明、伪代码、文件计划、env/compose、测试表和拟冻结结论逐项核对；尤其不要在摘要中保留已被后文增加例外的全称命题。

### 29.2 阻塞项（P0）

#### R6-P0-1：用户禁用没有 fencing 非 active 凭证，禁用后仍可新落一个 active 运行 Key

§8.4 的用户禁用事务只执行 `... WHERE id=? AND status='active'`。与此同时，§8.2 的创建者最终落 active 只校验 `status='creating' AND lease_epoch=:myEpoch` 与退休队列，不校验用户/绑定仍启用；janitor 又明确只处理 active scope，并把该行当前 token 排除在清理对象之外。

现实交错如下：

1. 首请求取得执行权，行处于 `creating`，远端 `POST /api/token/` 已发出或正在执行；
2. 管理员禁用用户；active-only UPDATE 对该行不命中，既不推进 `lease_epoch`，也不建立“该 scope 禁止再激活”的耐久状态；
3. 原创建者恢复，按原 epoch 成功 CAS 为 `active`；
4. 该 token 不在退休队列，janitor 又把它视为当前 token，因而不会禁用。门户绑定检查虽会拒绝正常网关请求，但远端运行 Key 仍保持有效，违反冻结需求 7.1.6“用户禁用后禁用或撤销全部 New API 运行 Key”，也失去凭证泄漏时的封禁能力。

`invalid` 行仍保存旧 token、用户禁用却只扫描 active 行，也是同一状态覆盖缺口。当前 v6 只是关闭了“active 换代”的集合冲突，尚未把“用户禁用”做成 scope 级终止状态。

**要求：**

- 用户禁用必须先建立耐久的 scope 级禁用事实，并使所有旧执行者失去写回权：至少对该用户全部 `runtime_credential` 行推进 fencing epoch/desired state，而不是只匹配 active；落 active 的 CAS 必须同时受“用户仍启用/该 scope 仍允许激活”的数据库级条件约束。
- 对行上已知 token，不论 active/invalid/其他持有 token 的状态，均要同事务清字段并入退休队列；对 `creating` 中“远端可能已创建、本地尚无 ID”的窗口，要在租约失效后按 scope 前缀做禁用收敛。该收敛不能依赖“janitor 只扫 active 行”，否则 disabled scope 的败者遗留仍无人处理。
- 增加确定性交错测试：禁用发生在 POST 前、POST 后/CAS 前、creating 被接管时、invalid 持有旧 token 时，以及禁用后旧 worker 恢复提交；最终断言用户所有 scope 前缀 token 均不可调用且本地不存在 active current。

### 29.3 重要缺口（P1）

#### R6-P1-1：风险占用的存储表示、部分索引和原子准入 SQL 不是同一个谓词

§3.6 与 §7.1 用 `orphan_candidate_ids IS NULL` 表示“零候选孤儿占一个槽位”；但 §6.2 的 INSERT 无条件写 `orphan_candidate_ids=:候选快照JSON`，没有规定零候选必须存 SQL NULL。自然实现若把零候选序列化为 JSON `[]`，它会被 `IS NULL` 谓词排除。反向地，§7.2 真正用于准入的 COUNT 仍写成全部未决 `orphan_remote`，会把有候选孤儿与候选 open 行重复计算；它也不再与 `idx_request_ledger_risk` 的部分索引谓词一致。§0#4 仍保留“全部未决 orphan”口径。

这会产生两种相反结果：按 §7.2 实现时有候选孤儿继续双占槽并造成假 429；按索引谓词实现但把空集合存为 `[]` 时，零候选孤儿不占槽。冻结用户是异常处置，不能替代事实源本身的确定表示，更不能消除插入与冻结之间的并发窗口。

**要求：** 增加显式 `orphan_candidate_count`，或规定并用 CHECK 约束“零候选只能存 NULL、非零候选必须是非空 JSON 数组”；把唯一一份 `riskHolding` SQL 谓词逐字复用到部分索引、原子准入、管理页统计、对账与测试。真实 libSQL 测试至少覆盖 SQL NULL、JSON `[]`、一候选、多候选以及 9/10 临界并发。

#### R6-P1-2：waived 的 `-W/+W` 只有业务描述，没有可验证的资金事务

§6.2 把 waived 描述为写 `request_charge -W` 与 `charge_reversal +W`，但没有定义同一事务中的关键字段和顺序：`charged_micro_usd` 是否写 W、孤儿何时写 `resolved_at/resolve_outcome`、reversal 如何填写 `reversal_of_id`、两条流水各自的 `balance_after_micro_usd`、物化余额更新一次还是两次，以及透支冻结在扣费后还是净额归零后判断。

这与现有不变量存在直接冲突：§3.6 声明“`charged_micro_usd` 非空 ↔ 存在 request_charge 流水”；若 waived 只写 `waived_micro_usd`，该不变量立即失败。若直接复用普通结算四步，`-W` 后可能触发 `overdraft_auto`，随后 `+W` 虽恢复余额，用户仍会因“解冻只允许人工”而被错误冻结。

**要求：** 为 waived 给出独立、完整的条件事务：先以 `resolved_at IS NULL` 守卫取得裁决权，明确 `charged_micro_usd`/`waived_micro_usd` 的各自语义，插入原扣费与带 `reversal_of_id` 的冲正，正确写两条余额快照并使物化余额最终净变为 0，最后只按**事务最终余额**评估冻结；任一步或候选吸收 `affected=0` 都整体回滚。增加临近冻结阈值、重复裁决、候选同时被处理三类测试。

#### R6-P1-3：统一后的 RSS 公式仍把“原始字节预算”误当作“实际驻留内存预算”

入站侧虽然取消了完整字符串和对象树，但设计没有规定 raw Buffer 的构造算法。常见的 chunk 列表 + `Buffer.concat` 在拼接瞬间至少同时保留约 B 字节 chunks 与 B 字节最终 Buffer，尚未计 undici 发送侧副本；默认放大系数 1.5 因而不是可证明上界。

响应侧问题更明确：§4.4 最多保留 32MB 原始解析缓冲，随后仍整体 `JSON.parse`。解析时会同时存在 Buffer、UTF-16 字符串和对象树；大量短字段可使 heap 远高于输入字节，而 `GATEWAY_PARSE_BUDGET_TOTAL` 只按 chunk 原始字节记账。故 §4.3 的 `RSS 峰值 ≲ body budget + parse budget + ...` 仍不成立，记账器未超 256MB 时进程依然可能 OOM。

**要求：** 明确入站缓冲的分配/拼接策略并把瞬时副本计入 charge；响应 usage 改为受限扫描/流式提取，或给解析阶段单独的、由实测证明的内存放大预算与更小硬上限。压力测试须分别构造无 Content-Length 的最大 chunked 入站体，以及含大量短字段/深层结构的非流式响应，同时断言 RSS、heap、external 三项峰值，而不只断言预算计数器。

#### R6-P1-4：三态 Caddy 模型不能同时表达“切流前 legacy”与“切流后 legacy 回滚”

§13.2 声明 maintenance 起 `newapi /v1*` 永久 404；但 §13.2 的状态定义又规定 `legacy` 下 newapi 域名“照现状”，而回滚及 §0/§18 均要求把 API mode 退回 legacy、api2 指向 3001。于是 portal→legacy 回滚会重新开放公网 `newapi.apipool.dev/v1*`。观察期内旧 `pk_` token 尚未删除，这会恢复一个文档刚声明“永久屏蔽”的额外直连入口，单一三态无法区分“首次切流前”和“已经越过永久屏蔽点后的回滚”。

生效协议也仍有歧义：§13.2 步骤 4 在 Caddy 尚为 maintenance 时先“恢复充值开关”，步骤 5 又恢复一次，与“①.5 和②之间无外部流量”冲突；`cutover.sh` 的通用顺序只写“生成并 validate→重建→探针”，未把每条边何时 `caddy reload` 及失败后的安全回退顺序定义完整。

**要求：** 将 pre-cutover legacy 与 post-cutover rollback 拆成不同状态，或增加越过切流点后单调不可逆的 `newapi_public_v1_blocked` 事实；所有 maintenance/portal/rollback 状态均保持 newapi 404。为每条状态边明确“冻结充值、重建容器、reload Caddy、探测、失败回退”的安全顺序；充值保持冻结直到 portal 探测通过，smoke 采用受控内部路径或在开放后执行。

### 31.2 非阻塞兼容项（进入计划，不阻塞设计冻结）

#### R7-P1-1：现有“恢复已停用用户”动作尚未定义 runtime credential 的恢复边

现有代码保留 `src/features/newapi-bridge/server/portal.ts::restoreNewapiUserBindingForAdmin`，会把 `newapi_user_binding` 从 disabled 恢复到 provisioning/active；但 v7 §8.2 对 `runtime_credential.status='disabled'` 只返回 403，§8.4 用户禁用又会把该用户全部 runtime 行永久置 disabled。若保持现有恢复入口不变，管理员界面会显示用户已恢复，但其 API 请求仍无法重新取得运行 Key。

这是可用性/兼容性缺口，不是首发安全阻塞：当前行为 fail-closed，不会产生绕权、错扣或数据损坏；项目尚无真实用户，也可人工处置。因此允许进入计划，但在实现用户禁用任务前必须二选一：

1. **支持恢复（推荐）**：绑定恢复成功后允许 runtime 行以换代型 `disabled → creating`（generation/lease_epoch +1、prev=NULL、当前 token 字段保持空）创建全新 token；disabled-scope janitor 入队前复核行仍为 disabled 且 epoch 未变，避免恢复并发时把新 token 当作禁用遗留。增加“禁用→恢复→首请求重建”及“恢复与 janitor 并发”测试。
2. **一期明确不支持恢复**：隐藏/禁用现有恢复入口并返回明确错误，把恢复能力列入后续任务；不能保留一个表面成功、数据面仍永久 403 的按钮。

### 31.3 实施备注（不新增设计 finding）

1. **不可逆闩的失败恢复**：§13.2 已规定屏蔽闩置 true 后不能回 legacy，因此 legacy→maintenance 首次转换失败时，不应再按通用文字“恢复可逆前态”；应保持/收敛到 fail-closed maintenance 后重试。实施计划需把每条边的 `caddy validate + reload`、容器重建、探测和失败落点逐条列出；这属于脚本实现细化，不影响四态方案本身成立。
2. **初期容量取舍可接受**：无 Content-Length 请求按 25MB 上限预分配、再按 2.0 计入 256MB 总预算，会牺牲并发利用率，但在初期低流量下属于合理的安全换简单。实现测试只需确认长度失真不会越界写、预算在异常路径释放，以及目标容器压测后调整放大系数；无需为提高少量并发重新设计流式落盘体系。

### 31.4 放行结论

- 设计可以从“候选 v7 / 待复审”转为冻结状态，并开始编写 `docs/plan/portal-newapi-routing-billing-decoupling/`。
- 计划必须显式纳入 R7-P1-1 的二选一决策、切流各状态边脚本任务，以及第 15 节既有资金/竞态/真实 smoke 验收；这些是实施任务，不再作为新一轮设计 NO-GO。
- 后续只有在实现或测试发现新的鉴权绕过、资金不守恒、重复扣费、不可恢复迁移或 portal 模式仍可绕过网关时，才重新打开设计评审；普通性能调参、文案和运维便利性进入 `docs/dev/.../issues.md` 或后续优化任务。

## 32. Codex 过度设计专项评审（v7，2026-07-14）

> **评审结论：设计正确性维持 GO，但首版实施范围存在明显过度设计，建议先减配再编写实施计划。** 第 31 节已经证明鉴权、资金一致性、风险准入和凭证收敛不存在新的设计级阻塞，本节不推翻该结论；问题在于 v7 同时建设了网关、钱包账本、运行凭证编排、渠道认证、价格证据、自动对账、分布式任务协调和完整切流/回滚控制面。对于项目尚未上线、初期流量不大的现实阶段，这会显著扩大实现量、状态组合和验收矩阵，而其中不少能力可以在出现真实运营信号后再补。
>
> 首版应收敛为：**强一致计费核心 + 少量模型/渠道白名单 + 单实例串行任务 + 人工异常处置 + 最小管理面**。资金正确性不能降级，自动化、自愈和多实例能力可以延后。

### 32.2 建议保留的首版硬核心

以下机制直接保护鉴权或资金正确性，不属于过度设计，不应因“低流量”而删除：

1. 门户 API Key 只保存哈希，运行时 New API Key 不向用户暴露；转发前剥离用户提供的凭证。
2. Caddy 在门户模式阻断用户直连 New API，确保所有需计费请求经过门户账本。
3. SQLite/libSQL 内完成原子风险准入；不能用进程内计数或“先查后插”代替。
4. `wallet_account` + signed micro-USD `wallet_ledger`，余额更新与流水写入同事务，并保留幂等键。
5. `request_ledger` 使用真实 request ID 唯一约束，保存 route/price version 快照；计费采用 BigInt 和统一单次向上取整。
6. 用量不确定时保持 `pending_backfill`/`unbilled` 并占用风险槽位；不得为了可用性猜测用量或静默放行。
7. 第一笔真实钱包写入前完成备份和恢复演练。

### 32.3 推荐的首版实施基线

首版可以控制在约 8～9 张核心业务表、2～3 类 worker 和 1 个内部管理工作台：

- 核心表保留 `portal_api_key`、`model_route`、`model_price_version`、简化后的 `runtime_credential`、`wallet_account`、`wallet_ledger`、`request_ledger`、管理审计表；仅在异步停用确有必要时增加 `credential_retirement`。
- `usage_worker` 合并直接回填失败、日志回填和 pending 超时扫描。
- `reconcile_worker` 合并批量同步、孤儿队列和钱包不变量检查。
- `credential_worker` 只负责必要的远端停用重试；若首版允许人工处理低概率异常，可由管理操作触发而不是常驻复杂 janitor。
- 首发模型和渠道采用显式白名单；证据维度不完整、渠道无法做可归因 smoke、成本上界不明确的组合暂不发布。
- 切流后以 maintenance + fix-forward 为主，不维持可重新接单的旧计费数据面。

### 32.4 延后能力的引入信号

延后不等于永久删除。建议只有在出现下列信号时，才把相应能力升级为独立 feature：

| 真实信号                                                    | 再引入的能力                                           |
| ----------------------------------------------------------- | ------------------------------------------------------ |
| 开始部署多个应用实例，或实际发生 worker 重叠执行            | 逐任务 DB lease、epoch fencing、heartbeat 与 row claim |
| 渠道数量明显增加，或渠道配置开始频繁变更                    | 自动 fingerprint、`channel_guard` 和逐渠道失效传播     |
| orphan 持续出现，人工裁决已形成稳定重复流程                 | 候选快照、自动吸收和批量裁决                           |
| 支持的模型出现复杂 cache/tool/audio 等计费维度              | 通用 price evidence、TTL 和受控推导                    |
| 压测或生产 RSS 证明简单硬上限造成 OOM/明显吞吐瓶颈          | 自定义受限扫描器和更精细的全局内存预算                 |
| 真实付费用户使长时间 maintenance 的业务损失高于双数据面风险 | 重新设计有明确账本边界的数据面回滚方案                 |
